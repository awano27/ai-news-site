OLLAMA × d3 ／ 業務連絡の仕分けを、どこまでAIに任せられるか

メールやチャットを、
手元のAIで3つに仕分ける。

「承認してください」「共有だけです」「先ほどの件、お願いします」。メールやチャットを読み直して、返信・承認・作業の依頼を拾う。PMや窓口担当が繰り返すこの作業を、「要対応・共有のみ・判断保留」の一次分類で助ける使い方を考えます。

d3は、あらかじめ決めた選択肢に沿って判定するAIモデルです。Ollamaの対応により、手元のPCで動かし、分類結果や確率を業務アプリへ返せます。今回の価値は、連絡を仕分ける仕組みを、ローカル環境で試す選択肢が増えたことにあります。[1][2]

この記事の結論：分類先が決まっていて、似た判定を何度も行う仕事が検証候補です。採用は、重要な依頼の見逃しを抑えつつ、確認・訂正を含む作業時間が減るかで判断します。

01

WHO / PROBLEM / CHANGE

決まった分類を繰り返す仕事が、検証候補になる

d3の用途として、公式は問い合わせの振り分け、文書の仕分け、案件の優先度判定などを挙げています。以下は、その機能を現場の仕事へ当てはめた本記事の活用案です。削減効果を測定した事例ではありません。[2]

PM・チームリーダー

承認や返信の依頼を
拾い直す手間を減らしたい

進捗報告と依頼が混在し、確認済みの連絡まで何度も読み返している。

要対応・共有のみ・判断保留の候補を一覧に付け、原文と担当を確認する。どの順番で表示するかはアプリで決めます。

測るもの：依頼の見逃し／到着から確認までの時間／訂正込みの作業時間

問い合わせ窓口・サポート担当

担当窓口の迷いと
転送の往復を減らしたい

「請求」「返品・交換」「操作・障害」のどこへ回すか、本文を読み直している。

担当窓口と情報不足を別々の問いにして判定。人が候補を確認してから引き継ぎます。

測るもの：誤った窓口への振り分け／転送回数／初回確認までの時間

業務アプリ・AIアプリの開発者

毎回の短い分類を
共通のAPIで扱いたい

文面に応じた処理の振り分けを、個別プロンプトや複雑な条件分岐で実装している。

質問と選択肢を定義し、APIの返り値で分岐する。FAQ参照・専門モデル・人への確認など、行き先の候補を判定します。

測るもの：振り分け後の品質／総費用／待ち時間／人への確認量

減らしたいのは「同じ連絡を何度も仕分け直す時間」

まずは人が原文を確認する一覧を作ります。「要対応」と出たことは、承認してよいことや、自分の担当であることの確定ではありません。担当チームや必要な前後の会話を入力に含め、実際に手間が減るかを確かめます。

02

WHAT CHANGED?

d3をOllamaのコマンドとAPIから呼び出せる

10月24日のv0.40.11リリースノートで、Ollamaがd3対応を案内しました。d3の開発元はvLLM Semantic Router。開発元資料には10月12〜13日の評価記録もあります。今回のニュースはOllamaから利用できるようになったことです。d3モデルページが示す必要条件は、Ollama 0.40.9以降です。[1][2][5]

入力は文章、項目を整理したJSON、静止画。質問ごとに「何を、どの基準で判定するか」を指定します。OllamaのSystem One APIでは、次の3種類を使えます。[2][3]

choice

決めた選択肢から選ぶ

「どの窓口へ回すか」「要対応か共有か」など。最有力の選択肢と、各選択肢の確率を返します。

説明付きの選択肢：2〜26個

noul

Yes / Noで判定する

「承認の依頼が書かれているか」など。Yesに当たる確率を0〜1で返します。

API上の型名は noul

score

低・中・高などで評価する

低い順に段階を定義します。返る値は、各段階の確率を使った平均値です。

順序付きの段階：2〜10個／番号は0から

同じ連絡へ、複数の問いをまとめて渡せる

「担当窓口」「承認依頼の有無」「緊急度」を1回のAPIリクエストに含められます。各質問は同じ入力を参照し、前の質問の回答が次の質問へ渡される仕組みではありません。結果に応じた順番や条件分岐はアプリ側で処理します。[4]

確率・confidence・scoreは、どう読むのか

確率：提示した選択肢に対するモデルの値です。「0.9」と出ても、現場で同じ判定が90%正しいと保証されたわけではありません。[2]

confidence：choiceとscoreで、どれかの選択肢をどの程度強く支持しているかを表します。これも正答率ではありません。[3]

score：「通常・本日中・即時」を0・1・2とすれば、値は 0×P(通常)＋1×P(本日中)＋2×P(即時) です。平均が1でも、「中間が有力」なのか「低・高に割れている」のかは異なります。重要な判断では分布も見られる表示にする、という設計が考えられます。後半はこの計算式から導く本記事の提案です。[3]

Ollama版d3は動画やBox／Track（位置や追跡に関する判定）に未対応です。開発元モデルの機能と、Ollamaで利用できる範囲は分けて読みます。[2]

03

DEFINE THE CRITERIA

分類名だけでなく、「どの条件なら入れるか」を決める

ここでは、誰かへの具体的な依頼があるかを分類します。自分の担当かは、人が別に確認します。追加対応が不要と明記されていれば「共有のみ」。依頼があるものの、何について何を求めているか特定できなければ「判断保留」とする例です。

要対応

誰かに承認・返信・作業を求めており、何について何をしてほしいか読み取れる。

共有のみ

報告や共有が目的で、追加の対応や返信が不要だと分かる。

判断保留

依頼の対象物や作業内容が不明、必要な文脈がない、または基準が競合する。

説明用の分類例 以下は人が作った期待結果です。理由の文章も編集上の説明であり、d3の実出力ではありません。

入力する連絡〈架空〉

金曜15時までに、見積案の承認または差戻しをご連絡ください。承認後に発注します。

この基準で期待する分類

要対応

承認または差戻しという行為を求めています。期限と、その後の発注も明記されています。

承認してよいかは、見積案の内容と権限を確認して別に判断します。

入力する連絡〈架空〉

本日の更新作業は完了しました。結果の共有です。追加の作業や返信は不要です。

この基準で期待する分類

共有のみ

作業完了の報告で、追加の作業も返信も不要と書かれています。

「返信」という単語だけで拾わず、「不要」の意味まで読めるかを確かめます。

入力する連絡〈架空〉

会議で話した件、いつもの流れでお願いします。

この基準で期待する分類

判断保留

依頼らしい表現ですが、この文だけでは対象と作業内容を特定できません。

会議の内容や前の会話を確認します。本文にない担当や作業は推測で補いません。

簡単な例の次に、否定・取消・共有と依頼の混在を試す
  • 取消の後に別の依頼：「昨日の確認依頼は取り消します。代わりに、修正版を確認して返信してください。」→ 要対応を期待。
  • 依頼の取消だけ：「本日の確認は不要になりました。先ほどの依頼への返信も不要です。」→ 共有のみを期待。
  • 共有と依頼が混在：「更新は完了しました。営業チームは新しい案内文を確認してください。」→ 要対応（営業チーム向け）を期待。自分の担当かは別に確認。

「判断保留」は本記事で設計した選択肢です。曖昧な文が必ずそこへ入る保証はないため、この種類の例を評価に含めます。

04

MODEL / RUNTIME / APPLICATION

d3は判定役。連絡の取得と確認画面はアプリで作る

Ollamaはモデルを動かしてAPIを提供する仕組み、d3は判定するモデルです。Teamsやメールの取得、原文へのリンク、一覧の並べ方、訂正の記録は周辺アプリの役割です。まずは連絡を手で貼り付け、判定候補と原文を並べる構成から検証できます。

入力でそろえるもの

本文と、判断に必要な前提

連絡本文、必要な前後の会話、対象チーム、基準日、分類条件を渡します。「今日」「こちら」「例の件」が何を指すか分からない入力は、先に情報不足として扱う設計にします。

画面で見せるもの

原文と、訂正できる分類候補

原文へのリンク、分類候補、選択肢ごとの値、確認状態を並べます。APIエラーや文脈不足は「共有のみ」に落とさず、確認待ちの一覧へ戻します。

実装例：CLIとローカルAPIへの渡し方

以下は公式の呼び出し形式を使い、この記事の架空例に置き換えた未実行の実装例です。Ollama 0.40.9以降とモデルの準備が必要です。[2][3][4]

CLI：3つの選択肢で分類する

ollama run d3:2b "本日の更新作業は完了しました。追加の作業や返信は不要です。" --ask "この連絡を分類してください。追加対応が不要と明記された報告はinfoです。依頼があるものの、何について何を求めているか特定できない場合はholdです。" --choice "action=誰かに具体的な承認・返信・作業を求める依頼" --choice "info=追加の対応が不要な報告や共有" --choice "hold=依頼の対象物や作業内容が不明、文脈不足、または基準が競合"

モデルが未取得の場合、ollama runによってダウンロードが始まります。上の例は短い1件の動作確認用です。

API：POST http://localhost:11434/v1/systemone

{
  "model": "d3:2b",
  "state": {
    "body": "本日の更新作業は完了しました。追加の作業や返信は不要です。"
  },
  "questions": {
    "category": {
      "type": "choice",
      "instructions": "bodyの連絡を分類してください。追加対応が不要と明記された報告はinfoです。依頼があるものの、何について何を求めているか特定できない場合はholdです。",
      "criteria": {
        "action": "誰かに具体的な承認・返信・作業を求める依頼",
        "info": "追加の対応が不要な報告や共有",
        "hold": "依頼の対象物や作業内容が不明、文脈不足、または基準が競合"
      }
    },
    "approval_request": {
      "type": "noul",
      "instructions": "bodyに承認を求める依頼が明記されていますか。",
      "criteria": {
        "true": "承認を求める依頼が明記されている",
        "false": "承認を求める依頼が明記されていない"
      }
    }
  }
}

JSONをHTTP POSTの本文として送ります。選択肢はanswers.category.choice、各選択肢の確率はanswers.category.probabilities、承認依頼へのYesの確率はanswers.approval_request.noulから読みます。d3は理由の自由文や返信文を生成しません。

このHTMLの操作は例の表示切替・画像保存・コピーのみです。モデルや外部APIへの推論リクエストは送りません。

長い会話は、質問や基準を含めて入力上限を確認する

配布パッケージは4,096トークン設定です。タグ一覧の「256K」を、そのまま利用可能な長さとは見なしません。System One APIは長すぎる入力を自動で切り捨てないため、上限超過時はエラーとして確認待ちへ戻す処理を用意します。[2][4][9]

実装で押さえる制約：入力容量、複数質問、ローカル処理の範囲
  • 容量：ローカルのSystem One APIは、文章と質問スキーマが64 KiB以内、画像のbase64を含むリクエスト全体が32 MiB以内。さらに読み込んだコンテキスト長にも収める必要があります。[4]
  • 複数質問：同じ入力への質問をまとめられますが、質問同士は回答を受け渡しません。開発元の説明では質問ごとに計算するため、質問を増やしても同じ時間とは限りません。[4][5]
  • 処理場所：Ollamaはlocalhost経由でもクラウドモデルを呼べます。端末内で処理する設計ではローカルd3タグを使い、必要ならOLLAMA_NO_CLOUD=1でクラウド機能を無効にして再起動します。連絡取得アプリやログの保存先は別に確認します。[3][6]
  • 待受：Ollamaの既定は127.0.0.1:11434です。複数PCへ提供する場合は、その外側の認証やアクセス制御も設計します。[6]
05

CHOOSE BY THE JOB

必要なのは、分類か、情報の抽出か、文章作成か

d3を選ぶかどうかは、欲しい出力から考えます。Ollamaのローカル生成モデルでは、JSON Schemaを指定して情報を取り出す「Structured Outputs」もあります。決まった選択肢への判定と、自由な項目の抽出・文章生成を分けて比較すると、役割が明確になります。[3][8]

出力仕様を踏まえた本記事の使い分け案。速度・精度の優劣は未測定です。
方法向いている仕事この場合は別の手段も検討
ルール処理フォームの種別、部署コード、既知の条件で行き先が決まる。文面の言い換えや、省略された意図の判定が多い。
d3固定の選択肢・Yes/No・段階評価を、さまざまな文章へ繰り返し適用する。担当者名、日付、要約、理由文を自由な形で取り出したい。
生成AI＋JSON Schema本文から担当者・期限などを取り出す、要約する、返信案を書く。短い固定分類だけで足りる。形式だけでなく内容の正しさも検証が必要。
人による判断前提が足りない、基準が変わる、権限や組織の事情を判断する。定型的な仕分けの量が多いときは、候補提示で補助できるか検証する。

既存の項目や単純なルールで十分なら、それを比較の出発点にします。

AIアプリの「モデル振り分け」に使う場合

たとえば入力を「FAQ参照」「コード相談」「複雑な検討」「人に確認」に分類し、アプリ側の表で呼び出し先へ結び付ける設計です。ただし、質問の種類が分かることと、どのモデルなら十分な回答ができるかは別です。

行き先ごとの回答品質、費用、待ち時間を測り、同じ入力を直接処理した場合と比べます。外部送信の可否や利用権限は、文章の推定だけに任せず、既知の設定で先に制限する構成を提案します。

JevやOllayaとの関係は？

d3はvLLM Semantic Routerの判定モデルで、この記事はOllama上で動かす方法を扱っています。選択肢・確率を返す使い方には共通点がありますが、ローカルd3の利用にJevのAPIキーは必要ありません。「Jev Decision Index」は評価指標の名前です。APIや品質がそのまま置き換え可能かは、別途確かめる必要があります。[2][3]

OllamaとOllayaは名称が似ていますが、ここでの導入手順・仕様はOllamaのものです。

06

HARDWARE / COST / EVIDENCE

小さなモデルから、使うPCで確かめる

d3はApache 2.0で公開されています。ダウンロードしたモデルを手元で実行する構成では、外部の推論APIに対する従量課金は発生しません。一方、PC、電力、導入・更新、分類基準づくり、誤判定の確認には費用と時間がかかります。[2][6]

最初の比較案

2Bと標準4Bを、同じ例で比べる

端末の負荷を抑えるならd3:2bから。4Bも実行できる環境なら、同じ入力で見逃し、誤判定、待ち時間を比べます。大きいモデルが、その仕事で必ず費用対効果に優れるとは限りません。

公式の環境要件

WindowsはOSとGPUも確認

公式Windows資料はWindows 10 22H2以降と対応ドライバーを案内しています。本体用に少なくとも4 GB、モデルには追加のディスク領域が必要です。実際の速度とメモリは、使う端末で測ります。[7]

「速い」「高性能」という開発元の数値を、そのままPCの期待値にしない

開発元のd3-nanoモデルカードには、AMD Instinct MI325X上の測定としてテキスト1件の中央値13.4 msなどが掲載されています。これは元チェックポイントと特定の実行環境の結果で、家庭用PCのOllamaで測った値ではありません。[5]

同様に、公式モデルページのJev Decision Indexは、元チェックポイントの評価です。Ollama向けに数値表現を変えた配布パッケージや、この記事の日本語業務連絡の正答率へは置き換えられません。[2]

本記事では、未検証の「何倍速い」「何%工数削減」を採用理由にしません。入力準備・待ち時間・訂正まで含む実測で比較する方針です。

07

MEASURE THE WHOLE WORKFLOW

20件で基準を直し、別の例で見逃しと時間を測る

最初の架空20件は、分類基準の曖昧さを見つけるための出発点です。その後は、基準を調整した例と、最終確認の例を分けます。同じスレッドの似た文が両方に入らないようにし、実際の連絡の割合に近い例と、重要な難例をそれぞれ確認します。以下は未実施の評価案です。

① 重要な依頼を、確認から漏らしていないか

事前に決めた確認期限まで追跡した連絡について、期限までに確認されなかった要対応を数えます。「共有のみ」への誤分類に加え、保留・エラーのまま期限を過ぎた案件も含めます。時間内に人が確認した案件は含めません。

業務上の見逃し率 ＝ 確認期限を過ぎた要対応件数 ÷ 実際の要対応件数

② 余計な確認を増やしていないか

要対応候補のうち、実際に対応が必要だった割合を見ます。共有だけの連絡が大量に混ざると、人の負担が増えます。

適合率 ＝ 正しい要対応候補数 ÷ 要対応候補の総数

③ 保留へ戻すべき文を、断定していないか

保留率に加え、文脈不足なのに要対応・共有と決めた件数も数えます。保留を増やすだけで見逃しを減らしていないか、確認待ちの量と時間を見ます。

保留の件数と、保留すべき文を誤分類した件数を記録

④ 訂正まで含めて、作業は軽くなったか

入力準備、推論待ち、原文確認、訂正、確定までの時間を比較します。モデルの初回読込と、読込後の応答は分け、最大メモリとエラーも記録します。

同じ条件で、手作業・既存ルール・d3を比較

閾値を決めるときの考え方と、記録する項目

高い確率でも誤るため、「0.9以上なら採用」のような値を最初から固定しません。調整用の例で、重要なクラスの確率・上位候補の差・入力不足を見て確認待ちに回す条件を作り、別の例で見逃しと確認量を評価します。入力上限・通信・モデル読込のエラーは、スコアと分けて扱います。

記録するものは、Ollamaの版、モデルタグと配布形式、PCとメモリ、質問・選択肢の版、入力本文と長さ、人の正解、各選択肢の値、処理時間、訂正結果です。モデルや基準を変更したら再評価します。

閾値による確認待ちへの振り分けはアプリ側の提案であり、d3が提供する正確な棄権保証ではありません。

利用範囲を広げる条件

  • 重要な依頼の見逃しが、事前に決めた許容範囲に収まる。
  • 文脈不足とエラーを、人が確認できる場所へ戻せる。
  • 訂正や保留の処理まで含め、現状より作業時間が減る。
  • 普段のアプリと同時利用しても、待ち時間とメモリが許容範囲に収まる。

基準や構成を見直す条件

  • 否定・取消・担当の違いを、繰り返し読み違える。
  • 情報が足りない文を、高い値で断定する。
  • 候補の確認や訂正が増え、手作業より時間がかかる。
  • 既存の項目や単純なルールで、同等以上の結果になる。

採用理由は「PCでAIが動いた」から一歩進めて。
「必要な依頼を拾い、確認の手間が減った」ことを確かめる。
