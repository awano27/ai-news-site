AIコーディングの
次のボトルネックは、
人間の注意力。

OpenAIが公開した Symphony は、Codexのようなコーディングエージェントを個別セッションで操作する仕様ではない。Linearのような Issue tracker を制御盤にして、複数のAIエージェントを組織のワークフローへ接続するためのオープンソース仕様だ。

重要なのは、AIがコードを書けるようになったことではない。AIが速くなった結果、人間の注意力・優先度判断・レビューが、開発組織の新しいボトルネックになったということ。Symphonyはそこを設計し直す。

04 · Harness Engineering 勝負はプロンプト術から業務設計へ移る

AIをいくら導入したかではなく、AIが自律的に働ける仕事をどれだけ設計できるかが生産性を左右する。

CHAPTER 1 · NEW UNIT OF WORK

プロンプトから、チケットへ。

Symphony は単体のAIエージェントを強くする話ではなく、複数のエージェントを開発組織のワークフローに接続する話だ。AIに渡す仕事の単位そのものが、その場限りの「プロンプト」から、背景・受け入れ条件・優先度・レビュー履歴を持つ「チケット」へ移る。

Problem · 課題

人間がAIを監視しすぎる

速いエージェントを増やしても、進捗確認・失敗修正・追加指示・レビューを人間が捌き続ける限り、管理コストが先に限界へ達する。

Mechanism · 仕組み

Issue が制御盤になる

タスクごとに専用ワークスペースを生成し、Codexエージェントを走らせ、状態・ログ・PR・レビュー資料を Issue 中心に集約する。

Outcome · 効能

人間は判断に戻る

実装の逐次監督から離れ、どの仕事を渡すか、結果を採用するか、どのガードレールを強化するかに集中できる。

CHAPTER 2 · CONTROL PLANE

Issue が、AIエージェントの制御盤になる。

OpenAIの記事では、Linear のようなプロジェクト管理ボードをコントロールプレーンにし、各 Issue に専用ワークスペースと Codex エージェントを割り当てる設計が示されている。GitHub リポジトリ側の仕様は、まず SPEC.md として公開されている。

  1. チケット起票背景・目的・受け入れ条件・優先度を Issue に書く。ここがAIチームに渡す仕事の仕様書になる。
  2. 常時監視と Issue 検知Symphony がトラッカーを見張り、着手できる Issue を検知する。人間は個別セッションを開き続けない。
  3. ワークスペース複製Issue ごとに隔離された作業環境を立ち上げる。Blast Radius Zero の土台はこの分離にある。
  4. Codex 実行専用エージェントが実装、テスト、修正を進める。作業ログは Issue と PR に戻る。
  5. 自己レビュー失敗を見つけて直すループを挟み、CIや解析結果を揃える。人間に渡す前に、AI自身が成果の根拠を整える。
  6. PR作成と着地成果物はPR、テスト結果、レビュー資料として提出される。人間は証拠を見て採否を判断する。
CI Statusテストが通ったか、どの条件を満たしたかを機械的に確認する。
Static Analysis複雑度、型、Lint、潜在的なリスクをレビュー前に可視化する。
Walkthrough変更意図と動作確認を短い説明や動画でまとめ、人間の読み解き負担を下げる。

CHAPTER 3 · WORK SHIFT

操作する働き方から、マネジメントする働き方へ。

プロンプトはその場限りの依頼。チケットは組織の仕事の単位。Symphony の本当の価値は、AI に渡す仕事の単位を、個人の会話から組織の作業単位へ引き上げる点にある。

BEFORE · プロンプト時代 Prompt

「このコードを書いて」「このバグを直して」。基準も履歴もユーザーの頭の中にあり、組織には残らない。

→
AFTER · チケット時代 Ticket

背景・受け入れ条件・優先度・ステータス・レビュー履歴を持つ、組織の仕事の単位。AIはチームメンバーとして参加する。

CHAPTER 4 · SAFETY & COST

自由を与えない。安全に動けるレールを敷く。

AIエージェントを自律化する前提として、Symphony は Issue ごとのワークスペース分離を組み込んでいる。本番運用では、サンドボックス、ネットワーク制限、権限管理、対象 Issue の絞り込みも前提になる。

サンドボックス × 隔離 × 権限

Issue 単位でワークスペースを分け、エージェントがその外に出ないように設計する。サンドボックス、ネットワーク制限、権限管理、対象 Issue の絞り込み、テスト、レビュー基準、ログ保存が運用の前提となる。

LLM代より、業務設計コスト

Symphony 自体は Apache-2.0 のオープンソース。だが運用は無料ではない。Codex / API 費用、クラウド実行、CI、ログや動画ストレージ、そしてセキュリティ設計と Issue 設計の工数が常に乗る。重い順から並べると、特に重要なのは LLM 代ではなく業務設計コストだ。

  • Issue が曖昧 → AI は曖昧な PR を量産する
  • テストが無い → AI の成果を検証できない
  • レビュー基準が無い → 人間の確認コストは下がらない
Path Prefixエージェントが触れるパスを限定し、別領域へ逸脱させない。
Network None外部通信は原則遮断し、必要なときだけ明示的に許可する。
Policy Gate危険な変更、権限昇格、機密領域へのアクセスをルールで止める。
Tier 1LLM / Codex 利用料。1タスク単位では小さく見えやすい。
Tier 2インフラ、CI実行、ログ、動画、ストレージ。並列実行で増える。
Tier 3業務設計コスト。AIが読めるIssue、テスト、権限、レビュー基準を整える工数が最も重い。

LANDSCAPE · PERSONAL vs ORG

Hermes は秘書、Symphony はチーム。

同じ「自律AIエージェント」でも、Nous Research の Hermes Agent と OpenAI Symphony は問いが違う。前者は個人の隣に座る秘書を、後者は開発組織の中で Issue を取りに行くチームを設計する。

Hermes Agent · Nous Research

個人の AI 秘書

Slack、Telegram、Discord、WhatsApp、CLI から呼び出せて、過去の会話を覚え、スキルを作り、定期タスクを実行する。隣にいて業務を助けるAI。

Issue tracker をコントロールプレーンに、複数の Codex エージェントを並列運用する。レビュー資料を含めた成果物で組織のワークフローに参加するAI。

USE CASE · WHERE IT WORKS

Symphony は「丸投げAI」ではない。向いている仕事だけに効く。

参考PDFが強調しているのは、AIチームが機能する条件だ。成功しやすいのは、入力、受け入れ条件、テスト、レビュー基準が明確な仕事。逆に、要件が曖昧で人間の判断や探索が中心の仕事は、そのまま投げても失敗しやすい。

向いているタスク

  • バグ修正: 再現条件と期待結果が明確で、テストで確認できる
  • テスト追加: 仕様や入出力が決まっており、既存コードに沿える
  • リファクタリング: 振る舞いを変えず、CIで回帰を検知できる
  • 小さな機能追加: 受け入れ条件とレビュー観点をIssueに書ける

不向きなタスク

  • 要件が曖昧な新規設計: 何を作るべきかの判断が先に必要
  • セキュリティ影響が大きい変更: 人間の設計レビューが欠かせない
  • ドキュメント不足のレガシーコード: AIが文脈を読み違えやすい
  • プロダクト判断を含む実装: 技術ではなく優先順位の問題になる
Symphony を使いこなせる会社とは、AIツールを入れた会社ではない。AIが働ける形に、仕事を整理できている会社だ。 EDITOR'S NOTE · 2026-04-29

CHAPTER 5 · YOUR MOVE

90日で目指すのは、AI導入ではなく「AIが働ける環境」だ。

AI 活用の中心がプロンプトからワークフローへ移ると、必要な力もシフトする。参考PDFのロードマップは、最初から全社自動化を狙わず、Foundation、Pilot、Scaling の順に環境を整えることを示している。

Day 1-30

Foundation

AIが読めるIssue、SPEC、テスト、権限、ログを整える。まずは小さな低リスクタスクを切り出す。

Day 31-60

Pilot

1チーム、1リポジトリ、低リスクIssueで試す。成果証明パケットとレビュー基準を固定する。

Day 61-90

Scaling

対象Issueを増やし、成功率、差し戻し理由、コスト、レビュー時間を計測して運用ルールを更新する。

Always

Proof Review

プロセス監視から成果検証へ移る。提出された証拠を品質の入口にし、運用を改善し続ける。
