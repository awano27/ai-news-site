運用モデル · 自律型 AI チーム

AIに任せる会社ほど、仕事の渡し方を設計している。

仕事をチケットに分解し、隔離環境で走らせ、証拠つきで戻す。プロンプトの上手さより、仕事をAIが読める形に整える力が問われる。

01 · 制御盤 Issue tracker が司令塔になる

人間がプロンプトを打ち続けるのではなく、チケットの背景・目的・受け入れ条件をAIチームの作業仕様に変換する。

02 · 影響範囲ゼロ 自律性の前に、影響範囲をゼロへ近づける

ワークスペース分離、パス逸脱防止、ネットワークのデフォルト遮断が、自律エージェント運用の前提になる。

03 · 成果証明 「できました」ではなく、証拠を提出させる

CI結果、静的解析、複雑度分析、ウォークスルー動画を束ね、人間は逐次監視ではなく採否判断に集中する。

04 · 業務設計 勝負はプロンプト術から業務設計へ移る

AIをいくら導入したかではなく、AIが自律的に働ける仕事をどれだけ設計できるかが生産性を左右する。

第1章 · 新しい仕事の単位

プロンプトから、チケットへ。

渡す仕事の単位が、場限りのプロンプトから、背景・受け入れ条件・履歴を持つチケットへ移る。

課題

人間がAIを監視しすぎる

速いエージェントを増やしても、進捗確認・失敗修正・追加指示・レビューを人間が捌き続ける限り、管理コストが先に限界へ達する。

仕組み

Issue が制御盤になる

オーケストレーターが State Reconciliation を回し、トラッカーとリポジトリの状態を自律的に一致させる。Issue が組織資産化する。

効能

人間は判断に戻る

実装の逐次監督から離れ、どの仕事を渡すか、結果を採用するか、どのガードレールを強化するかに集中できる。

第2章 · 制御盤

Issue が、AIエージェントの制御盤になる。

Linear のような Issue tracker を制御盤に、各 Issue に専用ワークスペースと Codex を割り当てる。仕様は GitHub の SPEC.md で公開中。

  1. チケット起票背景・受け入れ条件・優先度を Issue に書く。仕事の単位は組織資産になる。
  2. Always-on Pollingオーケストレーターが Linear 等を常時監視し、State Reconciliation で着手すべき Issue を検知。
  3. 隔離ワークスペース複製1チケット = 1隔離 Git クローン。Blast Radius Zero の物理的土台。
  4. Codex app-server 起動JSON-RPC over stdio でエージェントをヘッドレス制御。専用エージェントが実装する。
  5. Ralph Wiggum Loop自己レビュー → CI エラー修正 → 成果提出を完結させる自律サイクル。人間に渡す前に AI が根拠を整える。
  6. Proof of Work 提出PR + CI 結果 + 複雑度分析 + ウォークスルー動画。人間は証拠を見て採否を判断する。
CI Statusテスト通過と受け入れ条件の充足を機械的に確認。
Static Analysis複雑度・型・Lint・潜在リスクをレビュー前に可視化。
Walkthrough VideoAI 自身が実装意図を解説する動画。人間の読み解き負担を劇的に下げる。

第4章 · 安全とコスト

自由を与えない。安全に動けるレールを敷く。

Blast Radius Zero ── 自律 AI の暴走を構造的に防ぎ、機密を守りながら自律性を最大化する。

4つの Safety Invariants

CWD Matchエージェントの作業ディレクトリと隔離 Git クローンの厳格一致を検証。
Path Prefix絶対パス正規化で .ssh/.env 等への脱出を構造遮断。
Sanitized Keysワークスペース名は [A-Za-z0-9._-] のみ。インジェクション排除。
Network Noneデフォルト遮断。必要時のみ明示許可。漏洩・不正取得を防ぐ。

失敗モード「AI Slop」

  • Harness 不備 → AI が大量の低品質 PR を量産 → レビュー渋滞で ROI 悪化
  • テスト無し → 成果検証不能 → 「できました」を盲信するしかない
  • レビュー基準無し → 人間の確認コストは下がらない
Tier 1LLM / Codex 利用料 — 1タスクあたり $1.09〜$6.30 (自律試行込み)。
Tier 2隔離 VM、CI 実行、ログ・動画ストレージ。並列実行で増える。
Tier 3Harness Engineering — AGENTS.md / WORKFLOW.md 整備の人的工数。最重量。

適用範囲 · どこで効くか

Symphony は「丸投げAI」ではない。向いている仕事だけに効く。

成功しやすいのは、入力・受け入れ条件・テスト・レビュー基準が明確な仕事。逆に判断や探索が中心の仕事は、そのまま投げても失敗しやすい。

向いているタスク

  • バグ修正: 再現条件と期待結果が明確で、テストで確認できる
  • テスト追加: 仕様や入出力が決まっており、既存コードに沿える
  • リファクタリング: 振る舞いを変えず、CIで回帰を検知できる
  • 小さな機能追加: 受け入れ条件とレビュー観点をIssueに書ける

不向きなタスク

  • 要件が曖昧な新規設計: 何を作るべきかの判断が先に必要
  • セキュリティ影響が大きい変更: 人間の設計レビューが欠かせない
  • ドキュメント不足のレガシーコード: AIが文脈を読み違えやすい
  • プロダクト判断を含む実装: 技術ではなく優先順位の問題になる

第5章 · これからの動き方

90日で目指すのは、AI導入ではなく「AIが働ける環境」だ。

いきなり全社自動化は狙わない。Foundation → Pilot → Scaling の順で「AIが働ける環境」を整える。

1〜30 日目

基盤整備

AIが読める Issue・SPEC・テスト・権限・ログを整える。まずは小さな低リスクタスクを切り出す。

31〜60 日目

試験導入

1チーム・1リポジトリ・低リスク Issue で試す。成果証明パケットとレビュー基準を固定する。

61〜90 日目

本格展開

対象 Issue を増やし、成功率・差し戻し理由・コスト・レビュー時間を計測して運用ルールを更新する。

継続

成果レビュー

プロセス監視から成果検証へ移る。提出された証拠を品質の入口にし、運用を改善し続ける。
