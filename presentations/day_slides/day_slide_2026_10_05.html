00

ONE-PAGE BRIEF

誰の、どんな仕事が変わるのか。

価値は「クリックできること」そのものではない。判断の前に必要だった情報集めを、検証しやすい成果物に変えること。

結論：まず候補になるのは、「画面でしか取れない情報を集め、確認メモにする仕事」。業務の承認や、本番データの更新を丸ごと委ねる話とは分けて考える。

公式確認 一次資料の仕様導入案 本稿の設計・具体例未検証 自社画面の動作・効果
01

WHO / PROBLEM / OUTCOME

「誰が使うか」ではなく、「どの手作業をなくしたいか」。

対象職種だけでは選べない。入力となる画面、今の手間、欲しい成果物を一組にして、適用する仕事を選ぶ。以下は実証事例ではなく導入仮説。

01 / PM・プロジェクトリーダー

会議前に、
状況を集め直している。

いまの課題
旧式の課題管理画面で状態・担当・期限を確認し、朝会用のメモに転記する。調べるだけで準備が終わってしまう。
どう変える
承認済みの対象一覧だけを読み、指定したルールで「確認すべき行」と未確認項目を分ける。優先度をAIの推測だけで決めない。
得たい成果物
IDと確認元が付いた
「要確認一覧」
効果の測り方
メモの照合・修正まで含めた準備時間と、期限・担当の読み漏れ。

人に残す：担当変更、期限の合意、催促の送信、優先順位の決定。

02 / 開発・保守エンジニア

GUIの設定値を、
一つずつ照合している。

いまの課題
設定ファイルやAPIを提供しないツールで、画面の値と承認済みの設定表を見比べる。調査メモも手で作る。
どう変える
非機密の指定項目を読み、基準との差分を表にする。表示されていない内部状態や原因は、確認した事実と分ける。
得たい成果物
項目・現在値・基準値の
「設定差分メモ」
効果の測り方
差分の見逃し、誤検出、手戻り、元画面への確認往復。

人に残す：変更の妥当性、本番への反映、再起動、秘密情報の取り扱い。

03 / QA・受け入れ試験担当

確認手順と結果を、
毎回書き起こしている。

いまの課題
自動テスト化しにくいデスクトップ画面を操作し、期待表示との違いと再現手順を文章にする。
どう変える
テスト環境で短い確認シナリオを試し、操作した範囲・表示内容・期待との差を整理する。未実行のテストは合格にしない。
得たい成果物
確認範囲を明記した
「再現手順・不具合候補」
効果の測り方
人が追試できる割合、記録の欠落、確認・修正を含む報告工数。

人に残す：不具合の確定、試験の合否、品質保証、リリース判断。

これらの使い方は、公式が説明するデスクトップ情報の要約・GUI入力・アプリ間操作を業務に当てはめた提案です。各業務ツールとの互換性は保証していません。[1][2]

適用前に一度止まる：その情報は、もっと直接取り出せないか。

API・CLI・MCP・ファイル・ブラウザ専用ツールで済むなら、まずその経路を選ぶ。GUIに残った部分だけにComputer Useを使うのが、GitHubの説明に沿った考え方です。[2][6]

02

BEFORE → AFTER

PMの朝会準備を、「集計」から「確認」に寄せる。

想定条件：APIやエクスポートが使えない課題管理画面。社内で許可されたテスト環境・テストデータを使い、対象IDを人が指定する。

STEP 1 / 人

対象を固定する

アプリ、一覧、10件のID、必要項目を指定。見せてよいデータを先に確認する。

STEP 2 / Copilot

読めた事実を集める

状態・担当者・期限を読み取る。未表示、読めない値、対象外の行を混ぜない。

STEP 3 / Copilot

確認メモにする

ID・項目・確認元を残し、不明点は別表へ。送信先のアプリには転記しない。

STEP 4 / 人

照合して行動を決める

元画面と突き合わせ、担当や期限の確認先を決める。状態更新・送信は人が行う。

成果物イメージ / 朝会用の確認メモ架空データ・抜粋 / 実行結果ではありません
対象 10件全項目を確認 9件期限が未確認 1件登録・送信 実施しない想定
ID画面上の事実確認元人が次に確認すること
DEMO-021状態：未着手
担当：Aさん / 期限：10月8日		課題一覧 / DEMO-021行期限までの対応予定を確認する。
DEMO-022状態：確認待ち
担当：Bさん / 期限：10月9日		課題一覧 / DEMO-022行画面からは承認者が分からない。
DEMO-023状態：対応中
期限：未確認		詳細画面 / 期限欄が読めない期限を確認する。未設定とは断定しない。

実際の報告には確認日時・残りの対象行・未確認理由も記載する。10件を指定しただけでは、10件すべてが確認できた証拠にはならない。

① 行数ではなく、対象IDで照合

重複した行を2回読んで「10件」と数えない。指定したIDがそろっているかを確認する。

② 事実と提案を別にする

「確認待ち」は画面の状態。「Aさんに連絡すべき」は判断。推測で責任者を補わない。

③ 読めないことも成果物にする

未読や不明を明示すれば、人はそこを重点確認できる。ただし初回は読めた項目も全件照合する。

ワークフローと帳票は本稿の設計例です。公式の読み取り中心の依頼例と、人による結果確認の注意に基づきます。[3][4][6]

03

HOW IT WORKS

「画像を見てクリック」だけではない。

画面の部品情報と、必要な視覚情報を使う

公式資料では、OSのアクセシビリティツリーと、視覚的な情報が必要な場合のスクリーンショットを使うと説明されています。常に画面全体を画像認識する、と決めつけるのは不正確です。[2]

できる操作と、正しく終えられる仕事は別

クリック、文字入力・編集、キー操作、スクロール、ドラッグ、アプリ間移動が機能範囲です。ただし、非標準部品や動的な画面、応答タイミングの変化で、誤操作・繰り返し・停止が起き得ます。[1][6]

「ローカルで操作する」ことは、「情報がPCの外へ出ない」ことを意味しない。

表示された情報はCopilotへの文脈になり得ます。加えて、Computer UseはCLIを起動した作業ディレクトリの外にあるデスクトップアプリにも作用します。フォルダーを分けただけで、業務画面まで隔離できると考えないでください。[6]

設計上の示唆：小さく観測できる仕事に分け、操作後の状態を確かめる。読み取りに使う情報の形式と、利用・保存条件の確認は別に行う。

04

CHOOSE THE RIGHT TOOL

全部をComputer Useに寄せない。

判断の順序は「直接取れるか → 手順を固定できるか → 画面理解が必要か」。下表の向き・不向きは、公式の特徴から導いた選定案です。

作業別の選定表。製品間の性能を実測比較したランキングではありません。

第一候補合いやすい仕事判断の理由・注意点
API・CLI・MCPなど構造化された連携IDでデータを取得する。決まった操作を、許可されたインターフェースから行う。GitHubは、直接完了できるツールなら構造化情報と予測しやすい結果を得やすいと説明。MCP自体が精度や安全性を保証するわけではない。[2][6]
ブラウザ専用ツール例：Playwright管理下にあるWeb画面の反復テスト。明確な要素と期待結果を照合する。ロケーター、待機、再試行、テストの隔離を使える。Webで直接扱える部分までデスクトップの見た目経由にしない、という選定案。[10]
手順を定義するRPA例：Power Automate繰り返し頻度が高く、操作手順と業務ルールを定義できる仕事。RPAもUI要素・セレクターを扱う。「RPAは座標だけ、AIは意味が分かる」という単純な対比は不正確。保守工数を含めて比較する。[9]
Computer Use画面とのやり取り直接使える連携手段がなく、表示内容を読みながら進めたい小さな作業。GUI専用ツールを候補にできる。ただし画面の変化に必ず追従する保証はない。最初は読み取り・下書き中心に絞る。[1][2]
人が操作・承認重要な判断と確定支払、顧客への送信、本番の更新、取り消しにくい処理。本稿では初回の対象外とする。AIの操作可否ではなく、誤りの影響と組織で許される責任分担で決める。

混同しやすい「別の機能」も整理する。

GitHub CopilotとCopilot Studio：本稿はGitHub Copilot CLI / appの機能です。Copilot StudioにもComputer Useがありますが、エージェントへのツール追加や対象マシンの設定を行う別の導入経路です。本稿のCLIコマンドをそのままStudioの操作手順としては使えません。[3][11]

Computer UseとDynamic workflows：前者は画面を操作する手段。後者は工程・並列処理・結果の引き渡し・確認ポイントをコードで定義する機能です。「収集 → チェック → 人の承認」を仕組みにする際の候補ですが、Computer Useの必須条件ではありません。[3][8]

05

GUARDRAILS / WHAT NOT TO DELEGATE

「しないで」と「できない」は、同じではない。

依頼文は目的を伝えるもの。業務データを守るには、ツールの許可設定、対象アプリの権限、実行環境も分けて考える。

アプリを許可した後も、毎クリック・毎送信前に確認が出るとは限らない。

承認表示はCLIの権限モードやappのTool Permissionsに従います。Always allowは同じPCのCLIとappで共有され、保存許可の削除だけでは実行中セッションのアクセスは取り消されません。[3][4]

避けたい失敗起こり得る場面最初の試行で取る対策案
誤クリック・誤入力別ウィンドウが前面に来る。表示が遅れる。ボタンの位置や状態が変わる。テスト環境で範囲を限定。操作者は画面を監視し、試行中は同じデスクトップで別作業をしない。
二重実行反応が遅く、成功したか分からないまま同じ操作を繰り返す。初回は登録・送信を対象外にする。将来更新を試す場合も、現在状態を確認せずに再実行しない。
見せてはいけない情報の混入一覧や通知、他のタブに個人情報・顧客情報・秘密値が見える。データの利用条件を確認し、加工済みのテストデータと必要最小限の画面を使う。記録の保存先も限定する。
画面内容による脱線画面上の文章や予定外の内容をきっかけに、依頼と異なる操作へ進む。対象外の操作を禁止し、予定外なら報告するよう依頼。依頼文だけに依存せず、権限と監視も併用する。
止めたつもりでも権限が残る保存許可だけ削除し、実行中のセッションや現在の操作を終了していない。現在の操作を止め、必要ならセッションを終了する。既に確定した変更は、停止とは別に確認する。

リスクの根拠は公式資料、右列はそのリスクに対する本稿の対策案です。対策を取っても誤操作がなくなる保証はありません。[2][4][6][12]

初回の対象外：支払・顧客への送信・本番データ更新・管理者設定・実データの一括出力。重要な操作を広げる前に、対象システム側の制御と社内承認を別途整備する。

06

GET STARTED / WINDOWS & macOS

先に、使える条件と止め方を確認する。

以下は既にGitHub Copilot CLIまたはCopilot appを導入している人向け。機能は既定で無効。まずアカウントへの提供、対応OS、組織ポリシーを確認する。[2][3][4]

入口 A / GitHub Copilot CLI

対話セッション内で操作する

  1. 権限モードと現在状態を見る以下はPowerShellへ直接貼るコマンドではなく、Copilot CLIの対話セッションで入力する。
    /permissions show
    /computer show
  2. 組織で許可されていれば有効化
    /computer on
    機能が利用不可なら、アカウント・OS・ローカルセッションの条件を確認する。
  3. 限定した読み取りを依頼許可表示が出たらアプリと操作を確認。初回から広い自動許可を与えない。
  4. 試行後は無効化と状態確認
    /computer off
    /computer show

CLIの具体的な操作と条件。[3]

入口 B / GitHub Copilot app

設定画面で有効化する

  1. 現在の承認設定を見るSettings → SessionsでTool Permissionsを確認する。
  2. Computer Useを有効化Settings → Computer Use → Enable Computer Use。機能が見当たらなければアカウントとOSの対応を確認する。
  3. macOSはOS権限も確認AccessibilityとScreen Recordingが必要。Windowsに同じ名称の権限手順を当てはめない。
  4. 終了後に保存許可も見直すComputer UseのAlways allowed appsを確認。不要な保存許可を削除し、必要ならセッションも終了する。

appの具体的な設定と許可管理。[4]

CLIの今の操作を止める

Escを2回。予期しない動作なら、まず割り込む。[3]

appの今の操作を止める

StopまたはEsc。セッションのアクセス取消にはセッションを終了する。[4]

組織が禁止している場合

features.computerUse=falseはローカルでは上書き不可。回避するのではなく管理者に確認する。[5]

有効なのに動かないとき、どこを確認する？

CLIでは/pluginで組み込みのcomputer-useプラグイン、/mcp listでそのMCPサーバーの接続を確認します。macOSでは必要な2種類のOS権限も確認します。これで自社アプリの互換性まで保証されるわけではありません。[3]

CLI / app自体は全Copilotプランを対象とする案内がありますが、アカウントへの機能提供や組織のCLIポリシーも別に確認が必要です。Linux、VDI・リモートPC、無人運転を本稿では検証していません。[3][4]

07

VALUE / MEASURE THE WHOLE JOB

「AIが動いた」ではなく、「人の仕事が減った」で測る。

削減効果は、AIの操作速度だけでは決まらない。準備、監視、元画面との照合、誤りの修正、継続的な保守まで含めて比較する。以下は本稿の評価方法です。

導入効果を数える式 / 編集部の提案

1回あたりの人の工数削減

従来の人の作業時間
− 準備・監視の時間
− 確認・修正の時間

月次の正味削減

1回の削減 × 実行回数
− 月次の保守時間

人が画面を見張る時間も工数。AI実行にかかる経過時間と、使ったAI creditsは別項目で記録する。

計算例 / 数値はすべて仮定

10分の仕事が、何分減るか。

従来は人が10分。導入後に準備・監視2分、照合3分、修正1分が必要なら、削減は4分／回。

月20回で80分削減しても、保守に20分かかれば、月次の正味削減は次の値になる。

60分／月の人の工数削減

製品の実績や見込み値ではありません。この1時間の価値が、利用料金や運用負担に見合うかを判断するための例です。

測定項目記録するもの見落としやすい点
対象の網羅性対象ID数と確認できたID数、重複・欠落。同じ行を2回読んでも、対象が埋まったことにはならない。
内容の正確性状態・担当者・期限の一致と不一致、未確認の理由。「未確認」の申告と、「間違っているのに確定」は分ける。
安全性対象外操作、更新・送信、止めるまでの挙動。成功件数が多くても、重大な誤操作を相殺できない。
総工数・経過時間・費用準備・監視・照合・修正・保守、実行時間、利用量。人がずっと見守った時間を、削減時間として数えない。
料金の確認も、「月額を契約しているから無料」で止めない。

現在の公式課金案内では利用量をAI creditsで扱い、1 creditは0.01米ドル。消費額はモデルとトークン量に依存します。本調査ではComputer Use固有の追加料金や1業務あたりの消費量を確定していません。試行前後の利用量で確かめてください。[7][14]

Business / Enterpriseの予算には種類があります。組織などの予算額を設定するだけでなく、上限到達時に利用を停止する設定も確認します。ユーザー単位の上限とは動作が異なります。[13]

08

PILOT / GO OR NO-GO

最初の1画面で、「読める」と「任せられる」を分けて試す。

1画面・指定10件は、初回の範囲を小さくするための提案値。製品上限でも、安全性を保証するサンプル数でもありません。

試行前にそろえるもの

成果物の正解を、先に用意する。

  • 社内承認、見せてよいデータ、利用料金・予算を確認する。
  • 承認済みのテスト環境とテストデータを使う。可能なら対象アプリ側で閲覧専用アカウントを用意する。
  • 対象IDと項目を固定し、人が正解となる記録を作る。
  • 同じアプリ・モデル・OS・表示条件を記録する。
  • 現在の許可、操作の停止、セッションの終了方法を確認する。
本稿が提案する初回の判定条件

次の条件が崩れたら、拡大しない。

  • 対象外の更新・送信、機密データの混入がある。
  • ID・担当者・期限などの重要項目を誤ったまま確定している。
  • 指定対象の欠落を申告しない。未読を「問題なし」にしている。
  • 想定外の場面で止められない、または操作を繰り返す。
  • 照合・修正込みの総工数が、従来より増える。

通常の画面だけで終わらせず、条件を変えて再試行する。

期限欄が空白文字が途中で切れる一覧が複数ページ表示まで時間がかかる同じ見出しの別画面想定外の確認ダイアログ

想定外の操作を引き起こす実データや本番環境ではなく、許可されたテスト条件で確認する。単発成功を本番全体の信頼性に読み替えない。更新を許可する試行は、この読み取り試行とは別の承認・評価にする。

最初から夜間に放置して実行してよい？

本稿の初回案は人が監視するローカルの読み取り試行です。公開資料の機能範囲から、ロック画面・無人実行・リモート環境での完遂を保証できるとは判断していません。利用環境、停止方法、例外処理を別に確認してください。[3][6]

確認を人がするなら、導入する意味はある？

「情報を一から探して転記する時間」が「整理済みの材料を照合する時間」に変わり、その差が準備・修正・保守を上回る場合に意味があります。差が出ない仕事は、対象を変えるか、API・RPAなど別の経路を検討します。これは導入判断の考え方であり、時短が実証されたという主張ではありません。

09

READY-TO-TRY PROMPT

成果物と禁止操作まで含めて、依頼する。

下の [ ] を対象業務に合わせて書き換える。プロンプトだけで誤操作を防げるわけではなく、前節の権限・環境・監視と組み合わせる。

限定した一覧から、根拠付きの確認メモを作る

公式の読み取り中心の依頼例を参考に、成果物・対象ID・未確認の扱いを本稿で追加しました。これ自体は動作保証でも、技術的なセキュリティ境界でもありません。[3][4]

このニュースから、次に決めること

自社で1つ、「画面から確認メモを作る仕事」を選ぶ。

直接使えるAPIや専用ツールがないことを確かめ、限定したテストデータで読む。人の確認まで含めて仕事が減り、重要な間違いを検出できるかを見る。価値が出てから範囲を広げる。これが本稿の導入提案です。
