CURSOR ORIGIN

「コードはもう GitHub だけに置かない」——エージェント向け git forge を自前化した

Cursor が 2026年8月17日、自社コードホスティング Origin を有料プラン向け early beta としてロールアウトした。公式の定義は 「a git forge built for agent scale」。リポジトリ・プルリクエスト・コード閲覧・GitHub 同期をエディタ内に閉じ、Cloud Agents が Origin remote に対して clone / branch / commit / PR できるようにした。同日、GitHub は約8時間の大規模障害。3日前には SpaceX による約 $60B 買収がクローズしている。依存先が Microsoft から SpaceX 側へシフトしうる、即効性の高い一手である。

01

ONE-BOARD SUMMARY

1枚で見る Cursor Origin

Origin は、Cursor が自前でホストする git forge である。公式 changelog の一文は短い。「Cursor can now host your code.」

  • いま出せるのは essentials：repos / pull requests / コード閲覧 / GitHub sync。agent-native の本格機能は「soon」
  • 対象は Pro / Teams / Enterprise。無料プラン不可。アクセスは段階開放で、Enterprise 管理者は opt-out できる
  • GitHub を捨てる必要はない。同期 repo では GitHub が source of truth のまま、Cursor 内で閲覧・レビューできる

一次情報：Origin changelog / Origin docs / Forum 発表

価値評価

価値は大きい（しかも今日から試せる）。日常的に Cursor + GitHub を回しているチームには即効。ただし early beta であり、公開 OSS エコシステムや Issues / Actions の完全移行先ではない。

02

DIFFERENCES FROM EXISTING

既存の類似製品と何が違うポイントか

「AIエディタが GitHub に繋がる」は既にある。違いは ホスト層そのものを自前化したこと と、エージェントを第一級市民として設計したこと にある。

従来・類似GitHub + Cursor 接続

  • コードの原典は GitHub。障害・API制限・レートがそのままエージェントの上限になる
  • 人間前提の PR リズム（1日数 commit、順次レビュー）
  • エージェントは「外から clone して戻す」ゲスト
  • GitLab / Bitbucket も同じ人間ペースの forge

ORIGINエージェントの隣にコードを置く

  • Cursor 内の Codebase タブが拠点。clone / push は標準 git または Origin CLI
  • PR の diff・timeline・checks・コメント・merge をエディタ内で完結
  • Cloud Agents が Origin remote に対して clone / branch / commit / PR
  • GitHub を捨てずに mirror できる（移行の摩擦を最小化）
観点GitHub（従来）Origin + GitHub syncOrigin-hosted
source of truthGitHubGitHub のままOrigin
PR レビュー場所github.com両方（双方向・秒単位）Cursor / Origin
エージェント外部接続同じ UI から操作最も深い一体化
Issues / Actions本家当面 GitHub に残る初期は薄い
障害耐性GitHub 依存閲覧・エージェントは Origin 側で継続しやすいGitHub 非依存

最大の差別化は「もう一つの GitHub クローン」ではなく、エージェントが分単位で commit する前提で merge / CI / レビューを再設計すると宣言した点だ。6月 Compile のデモでは単一 repo で毎秒 22.6 commit、毎時約 29.6 万 clone、全球同期 <400ms を示した（本番 beta の公式ベンチではない）。

SO WHAT?

競争軸が「エディタの賢さ」から「エージェントが住むインフラを誰が握るか」へ移った。GitHub を残した mirror は、乗り換えではなく包囲網の入り口である。

04

TWO REPO TYPES

誰が何をホストするか——試し方まで

Origin には最初から 2つの repo 型がある。アイコンで区別され、同じ Codebase リストに並ぶ。

GITHUB MIRRORほとんどのチームの出発点

  • GitHub app を接続し、org / repo を選んで同期
  • 履歴・branch・tag・PR が来る。更新はリアルタイム
  • push は GitHub へ。GitHub が原典
  • PR コメント / リアクションは双方向、数秒で反映
  • Issues・Actions・secrets は当面 GitHub に残る
  • 切断はいつでも可。GitHub admin 権限が必要

ORIGIN-NATIVEコード資産を Origin に置く

  • Codebase タブ → New。Internal / Private
  • git remote 例：https://origin.cursor.com/{owner}/{repo}.git
  • 標準 git または Origin CLI で push
  • PR は Origin に残る（GitHub へは出ない）
  • エージェントから repo 作成も可能
  • early beta に正式資産を預ける判断が要る
STEP 1codebase 名を claim→ STEP 2GitHub を接続→ STEP 3小さい repo を sync→ STEP 4Cursor 内で PR 1本→ STEP 5Agent / Vercel を試す

最初の推奨は Mirror。正式な原典を GitHub に残したまま、エージェント同居だけ先に評価できる。

重要：これは GitHub の完成した代替ではない。公開リポジトリのネットワーク、企業向け保証、セキュリティ監査、Issues / Actions の厚みでは GitHub がまだ強い。Origin の面白さは「置き換え個数」より、AI が書いた変更を検証して正式状態へ上げる場所を Cursor が握ろうとしている点にある。

使い方

Cursor 中心なら Mirror で今日試す。Codex / Claude Code 中心で GitHub から離れる理由がないなら維持。代替を探しているなら Origin CLI まで含めて小さく試す。

05

AGENT SCALE

エージェントと Apps が repo の隣に来る

公式が繰り返すのは「Hosting code for agents is a different problem」という前提だ。人間は1日数 commit、エージェントは分単位。その速度では merge conflict と CI が製品そのものになる。

いま公式にできること

  • 閲覧中に聞く：Codebase / Web UI 上のコードに対してエージェントが回答・編集・PR 更新・branch push
  • Cloud Agents：隔離 VM 上の長期エージェントが Origin remote を clone / branch / commit / PR
  • ローカルエージェント：Origin CLI で repo 作成、remote 設定、初回 push まで実行可能
  • Vercel：PR ごとに preview。merge で production
  • Depot / Buildkite：既存 GitHub Actions workflow を走らせられる。Buildkite は native pipeline も
Cursor can now host your code. Origin begins rolling out today in early beta on all paid plans. We're starting with the essentials, designed for agent scale: repos, pull requests, code browsing, and GitHub sync. Agent-native features ship soon.— Cursor Changelog, 2026-08-17

プライバシーは namespace owner の Privacy Mode に従うと docs に明記。SpaceX 傘下になった直後なので、企業法務はデータ取り扱いを別途確認した方がよい。一部報道は「ホストコードの data terms がまだ薄い」と指摘している。

実務

今日の価値は「高速 clone の数字」より、コード・PR・エージェント・preview が同じタブに並ぶこと。agent-native 本丸はこれから。今は導線と権限モデルを身体で覚えるフェーズ。

06

STRATEGIC CONTEXT

GitHub 障害と同日、SpaceX 傘下での初の大型更新

Origin 単体の機能表より、置かれた週の方が雄弁である。

同日：GITHUB約8時間の広域障害

  • 2026-08-17、web / API で約 20% エラー
  • archive / raw ダウンロードは約 50%
  • Actions・PR・Webhooks・Copilot に波及
  • 8月中すでに複数回の障害が報告されていた
  • エージェントワークフローは上流障害で止まった

同週：SPACEX × CURSOR基盤を自前化する動機

  • 8/14 前後に約 $60B all-stock クローズ
  • Origin はその直後の初の大型製品更新
  • Microsoft（GitHub / Copilot）への依存を削る
  • エージェント生成コードの「正式化の場所」を握る
  • Colossus / xAI との垂直統合ストーリーと接続

同じ日に、「依存先が落ちる」と「依存先を自前化する」が並んだ。これは偶然の演出としても、構造的必然としても読める。エージェントの commit 頻度が上がるほど、ホスト層のレイテンシ・権限・障害はエディタ UX より重要な製品になる。

リスク：early beta に正式コードを置く判断。GitHub エコシステム（Actions、Marketplace、公開ネットワーク、監査）からの離脱コスト。SpaceX / xAI 傘下でのデータガバナンス。agent-native 機能が「soon」のまま停滞する可能性。

誰にとってサプライズか：日常的に Cursor + GitHub を使っている AI コーディングエンジニア。特に Cloud Agents / Automations を回しているチーム。GitHub 障害で手を止めた人。逆に、Codex や Claude Code 中心で GitHub をハブにしている人には、今日乗り換える理由はまだ弱い。

SO WHAT?

評価軸は「GitHub を何個置換したか」ではない。AI が書いた変更を、誰の場所で正式状態に上げるか。Origin はその争奪戦の開戦宣言である。

THE BOTTOM LINE

これは「新しい GitHub クローンが出た」ニュースではない。Cursor が、エージェント時代のリポジトリ層を自前で握ると宣言し、GitHub 障害と同日に使い始められる形で出したニュースである。
