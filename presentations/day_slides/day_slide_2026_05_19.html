§ 01Prologue · フロンティア・バイアスの終焉

なぜ小型ローカル LLM は「必然的に間違える」のか

現代のエンタープライズ AI 戦略はフロンティアモデルに依存する中央集権的クラウド型が主流だ。しかし「7B〜20B クラスに 405B 級の挙動をプロンプトで強いる」フロンティア・バイアスは、無益な計算リソース浪費とサンクコストの積み上げを生むだけ。小型モデルが直面する 5 つの構造的課題は、モデル単体の性能向上を待っても解決しない——必要なのは「失敗を前提にした周辺設計」だ。

巨大モデル依存から脱却し、小型ローカル LLM で実用的な AI コーディングを実現するアーキテクチャ——Intelligence-to-Environment Migration
5 つの壁 発生現象 技術的原因
コンテキスト崩壊指示の忘却、会話の迷子物理的 VRAM 制約と注意機構の解像度不足
ツール混乱JSON 形式の破損、誤呼び出し複雑なスキーマを正確に解釈する推論能力の欠如
ReAct ループ暴走同一の誤りを繰り返す無限ループ自己修正に必要な客観的視点の構造的不足
diff 破損既存ロジックの破壊、出力切り詰め全文生成時のハルシネーションと生成長制限
長期計画不能アーキテクチャ整合性の喪失階層的タスク分解能力の限界（Shallow Reasoning）
Before · 巨大モデル前提（柔軟型）

「万能な神」を待つアンチパターン

  • 情報入力：リポジトリ全体を読ませて文脈崩壊
  • ツール実行：完璧な JSON 出力を期待してエラーで停止
  • コード編集：ファイル全文出力を強いハルシネーション
  • タスク進行：自由な ReAct ループに任せて暴走
  • 結果：API コスト膨張・機密流出・主権喪失
After · 制御型（SmallCode）

「制御されたジュニア」として扱う

  • 情報入力：予算管理し構造（シグネチャ）に要約
  • ツール実行：寛容なパーサーで壊れた出力を自動修復
  • コード編集：レーザーメスのように1 行だけパッチ編集
  • タスク進行：TODO 駆動で外部メモリ化、検証ループ強制
  • 結果：オフライン完結・真の技術的自由を回復
Chapter 1プライバシー最優先の組織 — 機密コードを外部 API に送らない

金融・医療・官公庁の規制とセキュリティ制約を、完全オフラインで解く

状況： ISMS（情報セキュリティマネジメントシステム）準拠を求められる金融・医療・官公庁では、機密コードを外部 API へ送信できない規制が AI 活用の最大の障壁となってきた。SmallCode は完全なオフライン・閉域網動作を前提に設計されており、ISMS 適合性を維持したまま AI による生産性向上を実現する。

3 つの戦略的ペルソナ：プライバシー最優先の企業／ローカル環境のパワーユーザ／ドメイン特化型プロトタイパー
✓

結末 — テレメトリと自動 Web ブラウジングを原則遮断、ガバナンス担保

SmallCode は SMALLCODE_WEB_BROWSE=false をデフォルト維持し、テレメトリ送信やクラウドエスカレーションを原則遮断する。実行環境は DevContainer（隔離された開発コンテナ）で Ollama 等のローカル推論サーバーと通信し、AI による自動コミットを禁止。必ず「Human-in-the-Loop（人間の目視による git diff 確認）」の検収ゲートを通過させる。これにより、機密コードの流出・ガバナンスブリーチを構造的に防ぎ、完全オフラインのエアギャップ環境下で AI 支援を完結できる。

閉域網内ガバナンス：DevContainer + ローカル推論サーバー（Ollama 等）で知能を環境に委譲し、人間の目視 git diff を必須ゲートに
Chapter 2消費者ハードウェアのパワーユーザー — RTX 3060 で「24 時間ジュニア」を確保

高額クラウド API コストを、消費者 GPU で経済的に解消する

状況： 個人開発・SME（中小企業）にとって、Claude や GPT 級モデルの API 利用料は1 ヶ月単位で数万〜数十万円規模に膨らみ、本格的なエージェント運用の経済的合理性を破壊してきた。SmallCode は RTX 3060 等の消費者向け GPU や M シリーズ Mac でローカル実行することで、この構造を逆転する。

「万能な神」ではなく「制御されたジュニアエンジニア」として扱う——情報入力／ツール実行／コード編集／タスク進行の全フェーズでアンチパターンを反転
✓

結末 — 4B 活性モデルで単一ファイル 87% 達成、24 時間稼働ジュニアを経済合理性内で確保

SmallCode は実行ハーネスの最適化により、4B 活性の小型モデルでも単一ファイルタスクで 87% の達成率を記録（独自 100 タスク・ストレステスト）。マルチファイルタスクでは 46%、BoneScript 併用で 60%+ へ向上。これにより、外部 API へのロックインを完全に回避し、自社リソースで完結する分散型知能として「24 時間稼働するジュニアエンジニア」を経済的合理性の中で確保できる。注釈：この数値は SWE-bench 等の標準指標ではなく作製独自のストレステストに基づく自己報告値であり、PoC 指標として解釈する。

「環境の力」による実用域：単一ファイル 87%／マルチファイル 46%／BoneScript 併用で 60%+——小型 LLM のポテンシャルを PoC 指標で可視化
Chapter 3ドメイン特化型プロトタイパー — BoneScript で CRUD 自動化

DSL で15 回のツール呼び出しを 1〜2 回に圧縮する

状況： ドメイン特化型のプロトタイパー（社内ツール量産・PoC 開発）にとって、定型的なボイラープレート（DB 定義・ルーティング・認証・Docker 作成）は時間を奪う退屈なコーディングの代表格だった。SmallCode の戦略的差別化要因は、宣言的 DSL 「BoneScript」連携にある——複数ステップの推論を 1 つの宣言的 DSL に集約し、不確実性を排除して決定論的結果を得る。

The Chaos（不安定な 15 回のツール呼び出しが途中で経路絡まり破綻） → BoneScript コンパイラ（1 回の .bone ファイル生成で決定論的に完全なバックエンドプロジェクトが一瞬で組み上がる）
✓

結末 — Node.js/TypeScript 環境で 15 回 → 1〜2 回のツール呼出に圧縮、人間は設計に集中

通常のエージェントがファイル作成や DB 定義で「15 回前後のツールコール」を要するのに対し、SmallCode + BoneScript は「1〜2 回のコール」で完結。複数ファイルの整合性を保つという小型モデルが苦手とする「Shallow Reasoning（浅い推論）」を、コンパイラという決定論的システムへ委譲することで、モデルの「確率的な揺らぎ」を「確定的な成果」へ変換する。人間は「設計」という高付加価値業務に集中し、実装の「手」を完全に AI へ委譲する分業体制が確立される。注意：本機能は現時点で Node.js/TypeScript 特化であり、Python/Rust 等は標準的な手動生成へフォールバックする。

Chapter 4レーザーメス編集 — Patch-First でハルシネーションを物理的に封じる

ファイル全文の再生成を禁じ、「検索と置換」に絞り込む

状況： 小型モデルがファイル全文を生成すると、必ずTruncation（切り詰め）と既存ロジックの破壊が発生する。これは推論能力の限界というより生成長制限と確率的揺らぎから来る物理的な制約だ。SmallCode はファイル全体の再生成を禁じ、厳密一致による局所的な検索と置換（Search-and-Replace）のみを許可することで、この問題を根本から排除する。

アンチパターン「全文生成（爆撃）」で Truncation と既存ロジック破壊が発生 → SmallCode のパッチ優先編集（レーザーメス）は特定の 1 行だけを精密に置換し、周辺ロジックを一切傷つけない
✓

結末 — diff 破損・出力切り詰めの構造的リスクを物理的に排除

全文生成時に発生しがちなコードの書き落としやハルシネーション（Drift）を物理的に封じ込めることで、diff 破損や既存ロジック破壊という小型モデル運用の最大リスクを排除。さらに、不完全な JSON/YAML/プレーンテキストからツール命令を抽出し引数名の微細な間違いや型不一致を自動修復する Forgiving Tool Parser、tree-sitter ベースの構造解析で大きなファイルをシグネチャ要約に圧縮する Context Budget Engine と組み合わせることで、小型 LLM の「失敗モード」を実行ハーネス側で完全に吸収する。

§ 05The Scaffolding Engine

なぜ SmallCode は「揺らぎ」を「継続性」に変換できるのか

SmallCode の本質は、モデルの推論を無条件に信頼せず、周辺システムで補完する「デターミニスティック・フォールバック（決定論的予備手段）」にある。推論の「揺らぎ」を実行の「継続性」へ変換し、実務における工数削減効果を最大化する——その心臓部は 4 本の柱だ。

PILLAR 01

Patch-First Editing

ファイル全体の再生成を禁じ、検索と置換による局所的パッチ適用を主軸に。全文生成時のハルシネーション（Drift）を物理的に封じ込める。

PILLAR 02

Forgiving Tool Parser

不完全な JSON / YAML / プレーンテキストからツール命令を抽出し、引数名の微細な間違いや型不一致を自動修復。フォーマットエラー停止を最小化。

PILLAR 03

2-Stage Tool Routing

まずカテゴリ（read / write / search / run / plan）を選択させ、その後に詳細定義を提示。認知負荷と文脈消費を約 50% 削減。

PILLAR 04

TODO-Driven Planning

複雑タスクを原子的ステップ（TODO）に分解し外部ファイルで状態管理。一歩進むごとにテスト・リントで自動検証し、脆弱な長期推論を物理補完。

「万能な神」ではなく「制御されたジュニア」として扱う設計——情報入力／ツール実行／コード編集／タスク進行の全フェーズで安全装置を実装
# 環境要件：Node.js 18+ と Ollama 等のローカル推論サーバー ollama serve & ollama pull "gemma2:4b" # SmallCode を DevContainer 内で起動（テレメトリ・Web ブラウジングは原則遮断） export SMALLCODE_WEB_BROWSE=false smallcode init --provider ollama --model gemma2:4b # BoneScript（Node.js/TypeScript 特化の宣言的 DSL）でバックエンドを 1 回で生成 smallcode bone build api.bone --output ./services/api # Human-in-the-Loop：AI による自動コミットは禁止、必ず git diff で目視確認 git diff --stat && git add -p

Roadmap · 3 ステップ導入

段階的に PoC を積む

  • Step 1 Read-only：コードグラフ検索で構造把握（KPI = シンボル抽出の正確性・不要情報の混入率）
  • Step 2 Small Patch：単一ファイル内のバグ修正（KPI = パッチの妥当性・ハルシネーション発生率）
  • Step 3 Multi-file：TODO 駆動による複数ファイル実装（KPI = 自動テスト通過率・再試行回数）
  • 非機密領域での PoC から開始し、ガバナンス設定を社内基準に合わせて調整
  • ベンチマーク数値は過信せず、自社環境での PoC 結果を唯一の真実とする
Caveats · ラストワンマイルのハードル

導入前に必ず押さえる制約

  • 環境要件：Node.js 18+ が必須
  • Windows ビルド失敗リスク：better-sqlite3 / node-gyp のネイティブビルド失敗報告あり → WSL2 / macOS / Linux 推奨
  • BoneScript は Node.js/TypeScript 特化（Python/Rust 等は手動生成へフォールバック）
  • ガバナンス：SMALLCODE_WEB_BROWSE=false をデフォルト維持、Docker 隔離
  • 公式「87%」は SWE-bench 等の標準指標ではない（独自 100 タスクストレステストの自己報告値）
