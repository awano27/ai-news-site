02 / 08

誰の、どの手間が減るか

会話の合意を、そのまま実装の依頼へ

たとえば、QAが不具合を報告し、PMと開発者が修正方針を決めた場面。
その会話を起点に、権限を持つ担当者がCopilotへ作業を依頼できます。

従来の受け渡し

会話を読み直し、再現条件や決まった仕様をIssueや作業メモへまとめ直す。実装時に背景を聞き直すこともある。

連携を使った受け渡し

対象リポジトリと依頼を @GitHub に伝える。Copilotはスレッドの文脈を使い、調査や変更案の作成へ進む。

QA：再現条件を共有›PM・開発者：期待動作を合意›権限を持つ人：作業を依頼

変わるのは、相談から実装へ渡す部分。正しい仕様の合意、影響の判断、PRレビューは引き続きチームの仕事です。

この利用場面と効果の整理は本資料の解釈です。削減時間や品質の改善を実測したものではありません。

出典：GitHub Docs / 会話を使った作業

03 / 08

会話を起点にできること

調査から修正、PR作成まで依頼できる

まだ原因が分からない段階から始められます。
まず調査を頼むか、合意した修正を実装してもらうかは、依頼で明確にします。

バグを調べる

関連コードや会話の文脈を使って、原因を調査する。

Issueに残す

会話の内容から、追跡するためのIssueを作成する。

変更を実装する

修正内容を指定し、コード変更を進める。

PRを準備する

変更内容を、レビューできるPull Requestとして提出する。

依頼の例（本資料作成）
@GitHub　対象は example-org/shop、基準は main。検索結果の並び順が崩れる原因を調べ、修正案を先に説明してください。

調査結果を確認してから、実装・PR作成へ進める運用も選べます。PR作成と、マージ・本番反映は別の工程です。

11月6日の更新点

開始と、会話を続ける手順が改善

GENERAL AVAILABILITY

Slack・Teamsで一般提供

@GitHubを会話から呼び出し、調査や実装を依頼する連携が一般提供になりました。

FASTER START

メッセージからリポジトリを判別

依頼文にある対象を読み取り、同じリポジトリを選び直す手順を減らしました。

FOLLOW-UP

追加入力への応答を修正

続けて送ったメッセージへの応答が止まることのあった不具合を修正しました。

ATTRIBUTION

会話の起点と依頼者を明記

生成したIssueやPRの説明欄に、Slack／Teamsの会話と依頼者に由来することが示されます。

Teamsでは、さらにCanvasを追加。会話の横で計画やコード変更などを確認できます。

一般提供は「無料」「設定なしで全員が利用可能」という意味ではありません。利用条件は次のページで確認します。

06 / 08

導入前の条件と注意点

プラン・権限・会話の情報を確認する

プラン

有料のGitHub Copilotプランが対象。Slack／Teams側にGitHubアプリを導入し、GitHubアカウントを連携します。

権限

コード変更の開始・指示には、セッションで使う全リポジトリへのwrite権限が必要です。参加者全員に変更権限が付くわけではありません。

管理

組織のCopilotポリシーと、アプリが利用できるリポジトリを確認します。既存のアクセス権は引き継がれます。

スレッド全体が文脈になる

呼び出した一文だけでなく、スレッド全体を取り込み、生成する成果物にもその文脈を保存します。

無関係な顧客情報や機密を含む会話から、安易に呼び出さない。必要な情報だけをまとめた新しいスレッドやDMを使うと、対象を絞れます。

PRの確認・承認は既存ルールに従います。共有会話から作るPRはアプリ名義です。承認を要求するrulesetを使う場合、追加の承認が必要になることがあります。

出典：GitHub Docs / Slackの利用条件・セキュリティ　GitHub Docs / Teamsの権限・レビュー
