01

THE EDITORIAL VERDICT

まず、コードを探す仕事から。
全社検索への一斉導入は急がない。

「内容は説明できるが、名前や場所が分からない」仕事に向けた検索部品です。機能を追加できるかではなく、担当者が次の判断に必要な原資料へ戻れるかで価値を評価します。

編集部として最初に勧めるのは、対象を絞ったコード検索の比較試行。公式にはコード検索デモがあり、旧モデルからの評価改善も確認できます。一方、会議の判断根拠や不具合の類似検索は、業務データでの検証が必要な応用案です。[2][3]

採用する理由 / 見送る理由

試す理由：名前が分からない検索が多い。コードや資料を外部に送らず検索したい。

急がない理由：正確なID検索だけで足りる。既存検索で仕事が完了している。索引や権限を維持する担当がいない。

得られるのは「答え」ではなく「候補への近道」。原因の確定、最終決定の認定、コード修正の安全性は、別の検証や人の確認が必要です。
02

WHO / PROBLEM / SOLUTION / OUTCOME

あなたの「探せない」から読む。

同じモデルでも、利用者が必要とする成果物は違います。以下はすべて架空の業務例・構成案です。導入実績や時間短縮の実測値ではありません。

公式にコード検索デモあり

保守担当：処理の説明から、
読むべき関数を絞り込む。

例：「429が返ったあと、少し待って送信し直す処理はどこ？」

課題｜検索語を知らないと、調査を始められない

担当外のコードでは、処理の説明と実装上の命名が一致しません。何度も語を変えて検索したり、詳しい人に場所を聞いたりする段階が残ります。

解決｜自然言語と関数単位のコードを照合する

コードを関数・クラスなどに区切り、ファイル名、行番号、コミットと一緒に索引化。質問と近いコード片を提示し、IDEやリポジトリの該当箇所へ戻します。構成案：テキスト・コード用270M。シンボル名・エラーコードの検索も併用。

限界｜関連があっても、実際に呼ばれているとは限らない

検索順位は実行経路や原因の証明ではありません。呼び出し元、設定、テスト、対象ブランチは別途確認します。修正・テストを自動で済ませる機能でもありません。

測る｜正しい関数に着くまでの時間

担当者が選んだ正解関数が上位5件に入る割合と、正しい実装を開くまでの時間を既存検索と比較。完全一致で探せたシンボルを見失わないことも確認します。

期待する効果：初動調査・引き継ぎ負担の軽減

根拠：公式のtransformersコード検索デモはGemma 4＋Piエージェントと組み合わせた構成。EmbeddingGemma 2単体の自動調査ではなく、上記の業務効果も未測定。[3]

公式の会議支援例を、PM業務へ応用

PM：会議の前に、
「なぜそう決めたか」へ戻る。

例：「保存ボタンを連打できなくした理由を説明していた資料は？」

課題｜決定の根拠が、媒体をまたいで散らばる

仕様書のタイトルは覚えていない。録音を最初から聞く時間もない。探したい内容は説明できても、どの資料・会議を開くか分からない場面です。

解決｜文書・画面・録音の区間を同じ入口から探す

段落・ページ・録音区間を索引化し、検索結果に原本、ページ、時刻、更新日、文書状態を表示。候補を開いて「説明」と「承認された決定」を照合します。構成案：議事録テキストから開始。画像は追加170M、音声は追加300M。

限界｜録音が見つかっても、最終決定とは限らない

議論中の案と確定事項は、意味の近さだけでは区別できません。承認状態・版・日付の絞り込みが必要。逐語引用には文字起こし、要約には別の処理を用意します。

測る｜会議準備で、根拠を確認できたか

質問ごとに、正しい資料と該当区間まで到達できた割合を測ります。検索表示の速さだけでなく、原本確認までの時間と旧版の誤採用も記録します。

期待する効果：再説明・録音の聞き直しの削減

公式例：AI Edge ForesightはMac向け実験的会議支援アプリ。Windowsの既存業務ツールとの連携を保証する例ではありません。[5]

画像・テキスト検索能力からの応用案

QA・サポート：違う言い方の
「似た困りごと」を束ねる。

例：「保存後にぐるぐるのまま戻らない」＋画面キャプチャ。

課題｜利用者ごとに、症状の表現が違う

「固まる」「進まない」「保存できない」が別々の問い合わせになります。画像だけの報告もあり、製品名やチケット名だけの検索では比較しにくい状況です。

解決｜症状と画像から、参照する過去事例を探す

問い合わせ本文と画面画像を対象に、似た事例を候補化。製品・バージョン・端末条件で絞り込み、再現手順と回避策を担当者が確認します。構成案：テキスト＋画像440M。エラー番号はキーワード検索を残す。

限界｜画面が似ていても、原因や対処は別

類似事例を、そのまま解決策として自動返信しません。小さい文字や正確な番号が重要な場合は、原文・テキスト抽出も併用。機密情報入りの画像を無条件に共有索引へ入れない設計が必要です。

測る｜役に立つ既存事例が見つかったか

「画面が似ていた」ではなく、調査に使える事例が上位に入ったかを人が判定。別原因への誤誘導と、候補がないときに無理に返した件数も測ります。

期待する効果：既知事例の再発見・重複調査の削減

根拠は画像・テキストの共通表現と検索機能。問い合わせ対応での有効性は別途検証が必要です。[2][4]

公式に分類・ルーティングの例あり

自動化開発者：生成AIを呼ぶ前に、
処理の候補を振り分ける。

例：「ログインできない」を認証サポートの候補へ。曖昧なら保留。

課題｜自由文の入口で、次の処理を選びたい

入力のたびに大きな生成モデルへ問い合わせる前に、既知の業務カテゴリへ振り分けたい場面。対象は「処理の選択候補」であり、複雑な意思決定そのものではありません。

解決｜入力とラベルの説明を比較する

カテゴリ名だけでなく説明文もベクトル化し、入力との近さから候補を出します。自動化する範囲は限定し、低スコア・候補間の差が小さい・対象外の入力は保留する設計にします。

限界｜類似度を「正しい確率」と解釈しない

類似度0.8を、正答確率80%とは扱いません。閾値と保留ルールは実データで調整。承認、支払い、削除などの実行許可を、意味の近さだけで決めないようにします。

測る｜誤振り分けと、保留後の扱いやすさ

正解率だけでなく、カテゴリ別の誤振り分け、対象外入力の保留率、処理遅延を測ります。生成モデルの呼び出しを減らせても、手戻りが増えていないかを確認します。

期待する効果：入口の軽量化・処理候補の整理

公式AI Edge記事はMediaPipe Decision Taskでの分類・ルーティングを紹介。上記の保留・承認設計は編集部の提案です。[5]

03

HOW IT SOLVES THE PROBLEM

モデルが担当するのは、
「意味をそろえる」部分だけ。

テキスト、コード、画像、音声、動画を共通の768次元の数値表現へ変換します。同じ空間で比較できるため、検索文の言い回しと対象の表現が違っても、関連する候補を拾う検索を組み立てられます。[2][4]

取り込み時 / 編集部の構成例

1. 原資料を用意取り込みを許可された
コード・文書・メディア
2. 区切り＋参照情報関数・ページ・時間区間
原本、版、権限も保持
3. EmbeddingGemma 2各チャンクを
意味ベクトルに変換
4. 検索用の索引ベクトルとメタデータ
更新・削除にも追従
検索時：利用者の認証・権限で対象を限定 → 検索文をベクトル化 → キーワード検索と意味検索を併用 → 候補を並べる → 原本を開いて確認

モデルが提供するもの

意味ベクトルを作る能力。検索、分類、クラスタリングの材料になります。回答文の生成や、ユーザーごとのアクセス制御は別の機能です。[2]

アプリ側で実装・運用するもの

ファイル取得、適切な分割、権限フィルター、更新と削除、結果画面、原本へのリンク。回答を生成する場合は、その前に権限を適用し、別モデルを組み合わせます。[5][7]

段階的に広げられる理由：同じチェックポイントでエンコーダーを追加する場合、既存のテキストベクトルは再計算せず、画像・音声の索引を追加できます。別モデルや別の学習版への移行では、空間の互換性を仮定しません。[3]

「意味検索に置き換える」より、「完全一致を残して補う」。関数名、エラー番号、製品コードにはキーワード検索が有用です。BM25とベクトル検索をRRFなどで統合する方式を比較対象にします。RRFは順位を統合する仕組みで、EmbeddingGemma 2に内蔵された機能ではありません。[6][9]

EVIDENCE, NOT PROMISES

コード検索の改善は明確。
「仕事が速くなる」は、まだ別の問い。

旧モデルとの比較は、同じベンチマークの中で見ます。下記はGoogleの提供元評価で、全精度チェックポイント・768次元の結果。業務の時間短縮率でも、日本語での正答率でもありません。[2]

旧＝EmbeddingGemma 1。「コード」と「多言語」は異なる評価なので、2つの図の数値をそのまま比較しません。棒は各スコアの大きさを示し、成功率を表していません。

一次資料から確認できること

コード評価の改善、マルチモーダル入力、媒体ごとのエンコーダー選択、公式のコード・メディア検索デモ。[1][3][5]

この調査では確認していないこと

日本語の社内用語への強さ、個別PCでの応答速度、会議準備や保守時間の短縮、既存の社内検索より優れるか。いずれも実データでの検証事項です。

05

WHAT CAN BREAK THE USE CASE

導入の壁は、モデルの外にもある。

01 / LONG RECORDINGS

1時間の録音は、丸ごと入れない。

入力上限は共通の8,192トークン。音声だけなら最大約327秒という仕様です。長い会議は区間に分け、時刻を保持します。どの長さで区切ると必要な発言が見つかるかも評価対象。混在入力では各媒体が同じ枠を使います。[2]

02 / VIDEO IS NOT A TRANSCRIPT

動画対応でも、音声の扱いは確認する。

既定では動画を1fpsでフレーム化し、映像エンコーダーで処理します。音声トラックも自動で検索対象になると思い込まず、利用する入力経路を確認。発言内容を探すなら音声や文字起こしも組み合わせます。[2][4]

03 / SMALL MODEL ≠ SMALL APP

270Mは、必要RAMの値ではない。

テキスト・コードのみ270M、画像追加440M、音声追加570M、全構成740M。これはパラメータ数です。量子化、入力、索引、実行環境で総メモリーは変わるため、対象端末で測ります。[2]

04 / LOCAL DOES NOT MEAN AUTHORIZED

端末内でも、閲覧権限と削除は必要。

索引、回答生成、ログも含めて送信先を確認。共有索引では権限のない候補を表示・生成へ渡さない設計が必要です。退職・権限変更・原本削除に索引も追従させる運用を用意します。[2][7]

05 / JAPANESE & DOMAIN LANGUAGE

100以上の言語対応と、業務精度は別。

公式も言語間の性能差を認めています。日本語の略語、社内だけの呼び名、否定表現、似て非なる仕様を評価問題に入れます。一般ベンチマークの平均を、自社の検索成功率として使わないこと。[2]

06 / AVAILABLE VS. ANNOUNCED

提供済みと、予告段階を混同しない。

10月6日の公式発表では、AndroidのML Kit経由の提供は「今後数週間」の予定。Galleryの体験例、Pythonでの試行、ML Kitでの製品組み込みは、同じ提供段階ではありません。[5]

検索できることと、安全に自動化できることを分ける。「似たチケットを提示する」から始め、「同じ障害と断定する」「修正して本番へ出す」へ一足飛びに広げない設計を推奨します。
06

A SMALL, DECISION-READY EXPERIMENT

最初の検証は、1つの仕事と50問で。

以下は編集部の試行案です。実行結果ではありません。最初から全社データを入れず、取り込みの許可がある1リポジトリ、または少数の資料で、既存検索と比較します。

  1. 「検索できた」の定義を、先に決める

    コードなら正しい関数、PMなら承認済み資料と該当区間。単に関連しそうな候補が出ることを成功にしません。担当者が正解候補と許容範囲を作ります。

  2. 普通の質問と、失敗させたい質問を用意する

    例：言い換え25問、完全一致10問、似て非なる5問、該当なし5問、権限なし5問。調整に使う質問とは別に、最後まで触らない評価用の質問を確保します。

  3. 同じデータで、検索方式だけを変える

    キーワード検索、既存の埋め込みモデル、EmbeddingGemma 2単独、キーワード＋EmbeddingGemma 2を比較。まず768次元・同じ候補件数から始め、媒体の追加と次元短縮は後で分けて試します。

  4. 「原本を確認するまで」を計測する

    初回の取り込みと通常検索は別計測。検索の待ち時間だけでなく、人が正解を確認するまでの時間、誤誘導、ピークRAM、更新・削除の反映を記録します。

  5. 良かった範囲だけを、次の対象へ広げる

    コードで効果がなければ見送る。文書で有効なら画像を追加し、録音は別評価。モデル変更時は同じ次元でも空間の互換を仮定せず、再索引が必要か確認します。

採否を決める評価シート

Hit@5｜候補検索の成功率正解ありの質問のうち、正解が上位5件に1件以上入った割合。正解のない質問は別集計。
確認時間｜実際の作業時間質問開始から正しい原本を確認するまで。中央値と遅いケースを既存検索と比較。
安全性｜出してはいけない候補権限外の露出は0件を必須条件に。該当なしの誤提示、旧版への誤誘導も確認。
運用負荷｜続けられるか初回索引時間、検索p95、ピークRAM、削除・更新の反映時間を分けて記録。

数値目標は業務と端末の条件に合わせて事前に合意。50問の検証だけで本番の安全性を保証するものではありません。

実装担当向け：旧300Mモデルの手順と混同しない設定メモ

新モデル用の開発ガイドはSentence Transformers 6.1.0以降を案内しています。下記はテキスト・コード専用構成の設定例で、本調査でモデルの実行は未実施です。依存バージョン、モデルのリビジョン、実行端末を固定して検証します。[3][4]

import torch
from sentence_transformers import SentenceTransformer

model = SentenceTransformer(
    "google/embeddinggemma-2",
    device="cpu",
    config_kwargs={"vision_config": None, "audio_config": None},
    model_kwargs={"torch_dtype": torch.float32},
)
# コード検索の質問：prompt_name="CodeRetrieval"
# 一般検索の質問：prompt_name="SearchQuery"
# 資料：title: {ファイル名や資料名} | text: {本文}
# 次元を短縮する場合：truncate_dim=256,
#                     normalize_embeddings=True
# 質問と資料は、同じモデル空間・同じ次元で比較する。

通常の推論はbfloat16またはfloat32を用い、float16は避けるようモデルカードが指定しています。Documentはタイトルなしの形式なので、実際のタイトルを使う資料は公式書式で整形。画像・音声・動画にテキスト用接頭辞は付けません。[2]

導入判断は、「この探し物を改善できたか」。

コード探索に困っている：最優先で小さく比較。録音・画像が散らばっている：原本と区間を保つ設計から。今の検索で足りる：見送りも妥当。モデルの新しさより、見つけたい情報と運用の条件で選びます。

07
