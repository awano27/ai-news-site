2026.05.04 - Issue No.105 . open-design × Open CoDesign × Warp ADE

コーディングエージェントを「デザインエンジン」化する - Code-as-Design の本格運用

Figma/Sketch/XDの「ツール地獄」から、仕様→コード→ライブプレビュー の単一ループへ。
Hacker News 157票で話題の open-design（nexu-io/open-design）と、4/28 Open CoDesignの DESIGN.md 駆動を統合し、デザインを「描く」から「書いて生成する」へ。

2026年5月3日のHacker Newsで急上昇した open-design は、コーディングエージェント（Claude Opus 4.7 / GPT-5.5 / Codex）を「デザイン生成器」として再定義する OSS である。デザイナーがプロンプトと DESIGN.md（4/28発の設計トークン仕様）を書けば、エージェントが React / HTML / CSS の 動作するUI を即座に生成。Figmaの「ピクセル」を、コードという 単一の真実の源（Single Source of Truth） に置き換える。

本日提示するのは、open-design（生成エンジン）+ Open CoDesign / DESIGN.md（仕様トークン）+ Warp ADE / OpenAI Symphony（実行・並列化基盤）を直列接続する「Code-as-Design スタック」。デザイナー1人で3-5案を15分以内に並列生成し、エンジニア工数を介さずプロダクションコードに直結させる実装ガイド。

Chapter 01 - 課題

デザインと実装を分断する「翻訳コスト」

デザイナーがFigmaで作ったものを、エンジニアがコードで再現する。この 翻訳工程 こそが、現代プロダクト開発の最大のボトルネックである。

Problem . デザインツールの構造的限界

「Figmaで完璧だった」UIが、実装すると壊れる - その根本原因

デザイナーが3日かけて作ったFigmaファイル。エンジニアが実装に2日かける。レビューで「フォント、ボタンの間隔、ホバー挙動が違う」と指摘される。修正に半日。これが繰り返される。問題はエンジニアの腕ではない - デザインツールが「絵」を作り、実装が「コード」を作る という二重の真実が、最初から構造的な歪みを生んでいるのだ。

2026年、コーディングエージェントの推論能力が 人間デザイナーと同等のUI判断 を下せるレベルに到達した。ならば「絵」を経由せず、最初からコードで生成すればいい - これが open-design の出発点である。

Pain 01

二重の真実問題

Figmaは「絵」、実装は「コード」。両者の間で常にズレが発生し、デザインレビューが終わらない。

Pain 02

並列探索の困難さ

3案のUIを試すのに半日。Figmaの「描く」コストが、デザイン探索の幅を物理的に制約している。

Pain 03

ライセンス費用と囲い込み

Figma / Adobe XD / Sketch は商用ライセンス前提。OSSとローカル運用への移行需要が顕在化している。

Chapter 02 - エンジン

open-design - 「描く」を捨てて「書いて生成」する OSSデザインエンジン

GitHub nexu-io/open-design。Hacker News で 157 票を集めた、コーディングエージェントをデザイン生成器として駆動する OSS スタック。

Solution A . Code-as-Design

「プロンプト + DESIGN.md」が、Figmaのキャンバスを置き換える

デザイナーは design/landing-hero.md に「3カラム、左上にロゴ、CTA は緑、Hover で 4px 浮く」と書く。open-design CLI を叩くと、Claude Opus 4.7 が3案の React コンポーネントを並列生成し、localhost:3000 で並べてプレビューされる。気に入らなければプロンプトを書き換えて再実行。Figmaを開かずに、5分で「動く比較案」が手に入る。

核心は 「絵を描かない」 ことではない。「動くコードを最初から生成する」 ことである。生成物はそのままプロダクション投入可能で、エンジニアによる「翻訳」工程が消滅する。

FT.01 . Prompt → UI

自然言語からReact/HTMLを生成

デザイナーが書いた指示を、エージェントがコンポーネント単位で出力。Tailwind / shadcn-ui / vanilla CSS から選択可能。

出力は「動作するコード」。Figmaのエクスポート→コード化の二度手間を完全に省略する。
FT.02 . Parallel Variants

3-5案の並列生成

1プロンプトから複数パターンを並行実行。「保守的」「実験的」「アクセシビリティ重視」など軸を変えて同時生成。

Warp ADE と組み合わせると、各案を独立サンドボックスで起動・比較可能。デザイン探索の物理的制約が消える。
FT.03 . Live Preview

ホットリロード型のレビュー

生成と同時に localhost:3000 で表示。プロンプト修正→数秒で再描画。Figmaの「Save → Export → Sync」を排除。

レビュアーは「動作」を見て判断できる。Hover、フォーカス、レスポンシブ - 静止画では伝わらない要素を初期から検証可能。

Hacker Newsで VS Code Co-Authored-by Copilot（448票）と open-design（157票）が同日トレンド入り。前者は「AIコミット署名」、後者は「AIデザイン生成」 - 両方とも 「人間がやっていた中間工程をAIが奪う」 流れを示している。Code-as-Design はトレンドではなく、構造変化の兆候である。

Chapter 03 - 実装ワークフロー

4ステップで「Figmaなし」のデザインプロセスを構築する

既存のFigmaワークフローを 1日 でリプレースする最短手順。open-design + DESIGN.md + Warp/Symphony の連携で、デザイン→実装が 1ループ に統合される。

STEP 01

DESIGN.md を書く

4/28 Open CoDesignの仕様。色・フォント・コンポーネント原則を Markdown で定義。

STEP 02

open-design CLI 起動

npx open-design init で初期化。プロンプトに DESIGN.md を自動注入。

STEP 03

3案を並列生成

Warp ADE のサブエージェントで variant ごとに別プロセス実行。

STEP 04

レビュー → マージ

OpenAI Symphony の Issue tracker で承認。マージで即プロダクション。

# Code-as-Design 最小構成 (5分セットアップ) $ npx open-design init --design-md ./design/landing.md $ open-design generate "hero section, 3 variants, tailwind" --parallel 3 # 出力: variants/{a,b,c}/page.tsx + 即起動の dev server → http://localhost:3001 # Conservative → http://localhost:3002 # Experimental → http://localhost:3003 # A11y-first # 気に入った variant をマージ → 即プロダクション $ open-design promote variants/b --to src/app/page.tsx
Performance Note . 「描かない」が速い

Figmaで3案を作る平均時間：4-6時間。open-design + 並列生成：15分以内。さらに生成物が「動くコード」のため、エンジニア実装工数（通常 1-2日）も 消滅する。デザイナー1人 + AIエージェントで、従来の「デザイナー1 + エンジニア2」のチームに匹敵する出力を得る。

Architect's Note . 「Figma廃止」を急ぐな

open-design は強力だが、ブレインストーミング・ホワイトボード用途 では Figma / Excalidraw に分がある。当面は「構想は Figma、実装は open-design」の併用が現実解。完全リプレースは6-12ヶ月の段階移行で進めること。

Chapter 06 - 総括

5月4日の論点：「描く」から「書いて生成する」 へ - デザインの単一真実源はコードへ

2026年、デザイナーとエンジニアの境界は 「コード」という共通言語 に溶ける。open-design はその扉を開く OSS の一例にすぎないが、Code-as-Design という思想転換は不可逆である。

01

翻訳工程を消す

Figma → コードの再現作業を、エージェントによる直接生成で排除。エンジニア工数とレビュー時間が消失する。

02

並列探索を解放

1プロンプトから3-5案を15分で並列起動。デザインの「実験量」が物理的に拡大する。

03

仕様駆動を徹底

DESIGN.md を Single Source of Truth に。「絵」ではなく「仕様」がデザインを定義する。

04

OSS主権を選ぶ

SaaS依存（Figma/Adobe）から OSS+BYOK へ。データ主権とコスト削減を同時に実現する。

Closing . 4つの実践指針

Code-as-Design への移行 - 6ヶ月で完了させる4ステップ

Rule 01

まず DESIGN.md を書く

open-designを試す前に、4/28 Open CoDesignの DESIGN.md 仕様で社内の設計言語を固定する。

Rule 02

1機能で実証する

いきなり全廃せず、新規ランディングや小機能の「並列3案生成」で実証。チームの懐疑を実物で崩す。

Rule 03

レビューを Symphony で統制

承認フローを Issue tracker に集約。デザイン決定の履歴と理由を構造化して残す。

Rule 04

Figma は捨てない、降格させる

構想・ブレストには Figma を残し、実装フェーズだけ open-design に切り替える。段階移行が定着の鍵。

デザインを「描く」時代は終わる。仕様を書き、エージェントに生成させ、コードで議論する。
