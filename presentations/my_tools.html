01 / 代表作 · 判断の準備 / v1.4.0公開・mainで継続開発

kimeru

届いた依頼を、
人が判断できる材料に整える。

Windows・Teamsで働くPM向け。散らばる依頼を読み、対応手順をそろえます。文章生成AIを設定すると、不足情報・選択肢・返信案も用意。PMが修正・承認し、相手へ送るかを決めます。

  1. 1. 入力依頼・チケット・
    アラート・議事録
  2. 2. 下書き不足情報・対応手順・
    返信案をそろえる
  3. 3. 人の確認・承認原文と照合し、
    修正・承認・保留
  4. 4. 記録判断・作業・送信の
    状態を分けて残す

入力から、何が得られるか

入力は、QA環境停止による日程変更の相談。出力は「復旧見込み・残りのテスト日数・影響先」の確認事項、対応の5手順、返信案、確認履歴です。

原文にない約束を、承認前に見つける

体験の最初の返信案には、依頼にない「15時」が入っています。日付・数値の検査で注意を出し、修正・承認の流れを台本で再現します。画像はその修正後の記録です。

なぜ、人の承認を挟むのか

AIの案を決定や送信と取り違えないためです。承認しても作業完了にはしません。重大事象は規則で先に拾い、判断モデルと文章生成を分けて、迷った回答や情報不足に対する確認経路を設けています。

体験の実行手順（GitHub）↗設計の理由を読む ↗

Python 3.10以上で python -m kimeru try。APIキー不要。新しく取得したフォルダから試せます。

下書きの事実照合と、前例の参照を強化

v1.4.0では、原文にない人名や「対応済み」などの完了表現にも検査を広げました。必要に応じて過去の似た依頼や承認済みの言い回しを参照できます。前例の参照は設定で有効にする機能で、今回の事実確認と承認は引き続き必要です。

設計と開発の範囲

awano27による、生成AIを活用した個人開発。判断の流れ、承認境界、生成文の検査、検証条件をコードと設計資料で公開しています。各工程の人・AIの分担をたどれる資料は開発の進め方にまとめています。

AIに任せる範囲

既定の判定はキーワードによる簡易ルール。Kev・Jevを設定すると種類の判断を、writerを設定すると文面生成を担います。writerなしでは対応手順と定型文を返します。Codex writerは現在定型文にフォールバックします。

確認した版と検証状況

公開版はv1.4.0。確認したmainは79d14f7です。11月1日のCIはWindowsのPython 3.10〜3.12の3環境とLinuxの1環境、計4ジョブが成功。承認前の実行抑止、重大事象、情報不足、モデル停止、体験の隔離などを確認しています。

カードと一覧の返信状態をそろえる修正PR #2は統合済みです。Teams・ADO・一部モデル連携には作者の環境での確認記録があります。実データの判断精度・時間短縮と、開発に未使用のデータでの評価は今後の検証対象です。

実環境で使うとき

導入条件
Teams連携はWindows 10 / 11の画面操作です。表示や権限に依存するため、利用環境で確認します。Teamsの画面切り替えの問題が実機で確認されるまでは、自動運転を使わないようREADMEで案内しています。
保存と送信
判断・ログはPCに保存。Jev、設定したwriter、明示許可したリモートKevには材料を送ります。自分とのTeamsチャットへの投稿も送信を伴います。
操作の境界
相手への返信は既定では手動コピー。ADOコメント・優先度変更・相手への返信は、種類ごとの有効化と承認、実行操作を要します。スマホ受信、相手への送信、ADOへの書き込みなどはテストと実機確認を分けて扱っています。

02 / 作業の振り返り · 公開main

KaizenLog

PC作業の記録を、
読み返せる日誌にする。

日々の作業を振り返りたい人向け。ActivityWatchの記録から、Markdown日誌・日報の下書き・月次集計を作ります。ローカルのHome画面で成果や次に試すことを記録でき、日誌と集計はLLMなしで動きます。

入力例

出力例
「アクティブ時間1時間30分／開発67%・ブラウジング33%」と、本人が書く振り返り欄。

READMEの架空例です。作業の観測値と、本人が振り返って書く内容を分けて残します。

作った背景

作業ログがあっても、長い記録を毎日読み返すのは手間です。記録の集計、本人の振り返り、翌日に試すことを、日誌の中で見渡せる形にします。

設計で工夫したこと

  • 観測した事実はコードで集計し、任意のAI改善提案とは分ける。
  • ノートは管理する区間だけを更新し、その外の手書きメモを保つ。
  • 指標を測れない日は「未判定」、取得できない費用やトークンは「不明」として残す。

公開している成果物

日誌・Home画面の利用手順、AIへの依頼文草案をプレビューして明示保存する機能、開発指示と受け入れ条件を公開しています。月次の工数集計には、工数を含む日次統計が必要です。

03 / 残件・相手待ちの管理 · 公開開発版

dayloop

今日の仕事と、
相手の返答待ちを分けて追う。

朝の計画から夕方の残件整理までをつなぐ、Windows向けのツールです。公開開発版では、依頼内容・相手・次回確認日時を日別タスクとは別の台帳で管理。「返答が来た」と「自分の仕事が終わった」を分け、依頼の変更は本人が確認して履歴に残します。

紹介対象はcodex/requirements-gapの公開開発版（既定のmasterには未統合）です。下のリンクから、この版のREADMEを確認できます。

入力例
「設計レビューを依頼。水曜15時に返答を確認」。
出力例
相手待ちの台帳に、依頼内容・次回確認の予定・返答や変更の履歴を残す。日次タスクは別に整理し、終了時にMarkdown日誌へ書き出す。

公開の架空データに基づく説明例です。相手待ちは、1日を閉じても別の台帳に残ります。

開発版README・試用手順（GitHub）↗相手待ちの入力と履歴 ↗

Jevを使う場合は外部送信と条件付きの自動適用があります。手入力での試用は、外部連携を無効にする手順です。

過去の完了を、新しい仕事の完了証拠にしない

同じ名前のタスクを新しく登録しても、以前の「完了」を自動で再利用しないようにしました。さらに、終了済み日誌を通常の更新から守り、外部取込の失敗・部分取得を「依頼なし」と区別します。

完了判断の回帰テスト ↗日誌保全・取込処理の更新 ↗
dayloopの入力・出力、設計と利用条件を見る

作った背景

自分が動く仕事と相手の返答待ちを同じ一覧で管理すると、待っているだけの項目まで毎日持ち越すことになります。日次タスクの扱いを決めて1日を閉じ、約束は日をまたいで追う仕組みに分けています。

設計で工夫したこと

  • 扱いの決まらない残件があれば、その日を閉じない。相手からの返答だけでは自分のタスクを完了にしない。
  • 依頼変更は本人の確認と版番号を照合し、古い情報による上書きを防ぐ。
  • 選んだ結論と理由を記録して再利用する一方、過去の完了判断を新しい仕事の完了証拠にはしない。

公開している成果物

CLIとMCPで扱う約束台帳、日次ループ、判断履歴のコードとテストを公開しています。手入力で試す手順と、外部サービスに接続する手順をREADMEで分けています。
