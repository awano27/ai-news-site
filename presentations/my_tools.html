01 / 代表作 · 判断の準備 / 公開・検証段階

kimeru

届いた依頼を、
人が判断できる材料に整える。

Windows・Teamsで働くPMが、返答する前に不足情報と選択肢をそろえるためのツール。届いた依頼から、対応手順と返信の下書きを用意します。日程の判断と送信は、人が担います。

  1. 1. 入力依頼・チケット・
    アラート・議事録
  2. 2. 下書き不足情報・対応手順・
    返信案をそろえる
  3. 3. 人の確認・承認原文と照合し、
    修正・承認・保留
  4. 4. 記録判断・作業・送信の
    状態を分けて残す

入力から、何が得られるか

入力は、QA環境停止による日程変更の相談。出力は「復旧見込み・残りのテスト日数・影響先」の確認事項、対応の5手順、返信案、確認履歴です。

誤った約束を、そのまま送らない

体験の最初の返信案には、依頼にない「15時」が入っています。日付・数値の検査で注意を出し、修正・承認の流れを台本で再現します。画像はその修正後の記録です。

検査・承認待ち・修正履歴は実コードの処理。体験の判断値は固定値で、正解確率ではありません。

なぜ、人の承認を挟むのか

AIの案を決定や送信と取り違えないためです。承認しても作業完了にはしません。重大事象は規則で先に拾い、判断モデルと文章生成を分けて、迷った回答や情報不足に対する確認経路を設けています。

固定データの体験を試す ↗設計の理由を読む ↗

設計と開発の範囲

awano27による、生成AIを活用した個人開発。判断の流れ、承認境界、生成文の検査、検証条件をコードと設計資料で公開しています。各工程の人・AIの分担をたどれる資料は開発の進め方にまとめています。

AIに任せる範囲

既定の判定はキーワードによる簡易ルール。Kev・Jevを設定すると種類の判断を、writerを設定すると文面生成を担います。writerなしでは対応手順と定型文を返します。Codex writerは現在定型文にフォールバックします。

何を確かめたか

公開CIにはWindows / Linuxの回帰試験の成功記録があります。承認前の実行抑止、重大事象、情報不足、モデル停止、体験の隔離を対象にしています。架空データの経路試験と、Kev実モデルの評価は別です。開発に未使用のデータでの評価と実業務の効果測定は残っています。

カードと一覧の返信状態をそろえる修正PR #2は2026年10月18日にマージ済みです。同じコミットのCIには成功と失敗の記録があります。後者はWindows / Python 3.10の単体テストが失敗しており、マージ済みであることと検証結果は分けて確認します。

導入条件

操作の境界
相手への返信は既定では手動コピー。ADOコメントや相手への送信は、別途有効化・承認・実行操作が必要です。通知や外部接続の実機確認、実データでの評価は利用前に行います。

02 / 作業の振り返り · ソース公開

KaizenLog

PC作業の記録を、
読み返せる日誌にする。

日々の作業を振り返りたい人向け。ActivityWatchの記録を集計し、Markdownの活動日誌と日報ドラフトを残します。Obsidianでも読めます。

入力
ActivityWatchの作業記録と、その日の目標・振り返り。
出力
作業内訳、日報ドラフト、翌日のフォーカスをまとめたMarkdown日誌。

公開日誌の架空例では「配布物の確認」から「次回はチェックリストへ集約する」という振り返りを掲載。数値や成果は説明用で、実測の実績ではありません。日誌の全体を見る ↗

KaizenLogの入力・出力、設計と利用条件を見る

作った背景

作業ログがあっても、長い記録を毎日読み返すのは手間です。記録の集計、本人の振り返り、翌日に試すことを、日誌の中で見渡せる形にします。

設計で工夫したこと

  • 観測した事実はコードで集計し、AIによる改善提案とは分ける。日誌だけならLLMは不要。
  • ノートは管理する区間だけを更新し、その外の手書きメモを保つ。
  • 指標を測れない日は「未判定」、取得できない費用やトークンは「不明」として残す。

公開している成果物

架空データの日誌サンプル、利用ガイド、AIへの開発指示を公開しています。出力例だけでなく、読みやすさや計測の扱いを改善してきた過程も確認できます。

03 / 1日の計画 · ソース公開

dayloop

今日の予定から、
残件の扱いまで決める。

その日のタスクを整理して終えたい人向け。朝の計画、次に取り組む1件、夕方の残件整理を、ひとつのループにつなぎます。

入力
「仕様書レビュー」のタスクと、終わらなかった理由「レビュー待ち」。
出力
未完了の状態と理由を台帳に残し、全件の扱いを決めると、その日のMarkdownを書き出す。

利用ガイドに基づく説明例です。実行画面や実業務の記録ではありません。コマンドと出力条件を見る ↗

dayloopの入力・出力、設計と利用条件を見る

作った背景

予定を立てるだけでは、終わらなかった仕事が翌日に残ります。完了・未完了・持ち越し・取り下げのどれかを決めてから、1日を閉じる仕組みです。

設計で工夫したこと

  • 扱いの決まらない残件があれば、その日を閉じない。
  • 選んだ結論と理由を判断グラフに残し、同じ条件の判断に再利用する。変更は履歴を残して差し替える。
  • Jevに聞くのは過去の答えがない判断だけ。接続がない場合も、人が選んで進められる。

公開している成果物

コマンドごとの利用ガイド、判断グラフのコード、残件がある日は閉じられないことなどを確認するテストがあります。実機や外部接続の条件は、以下の利用条件にまとめています。
