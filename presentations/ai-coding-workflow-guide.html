開発・コード修正

AIにコード修正を任せる

直したい動作と、変えてはいけない動作を先に決める。AIに実装とテストを任せ、差分を人が確認する。

公式資料の確認日：2026年11月22日 ｜ 製品の比較実測：未実施

迷ったらこの構成

普段のエディターで、小さな不具合を1件直す。

既存のテストが動くリポジトリで、会社やチームが承認しているエージェントを使います。VS CodeでGitHub Copilotを使っているなら、まずエディター内のCopilotセッションから。モデルを選び直すより、再現条件と「どうなれば完了か」を先に渡すほうが、修正結果を確認しやすくなります。

使い分け始める3ステップ依頼文テンプレートレビュー出典

作業する場所で選ぶ

手元で一緒に直す

ローカル環境でしか再現しない不具合や、途中で方針を確認したい作業向け。承認済みのVS Code内CopilotやCLIのエージェントを、専用ブランチで使います。コマンドが手元で動くことと、モデルが端末内で動くことは別です。送信されるデータと権限は別に確認します。[1]

別環境にまとめて任せる

対象のリポジトリと動作条件が明確で、別環境でもテストが回る作業向け。たとえばGitHub上の対象リポジトリでCopilot cloud agentに小さな作業を割り当て、戻ってきたPRを確認。未pushの差分や自分のPCの環境に依存する作業は、手元で行います。[3]

VS Codeの旧「Local harness」とローカル実行は別です

旧「Local harness」はVS Code 1.146で非推奨となり、2027年2月に削除予定です。後継の「Copilot」でも端末でコマンドを動かせます。選択するだけでサンドボックスが有効になるわけではありません。[2]

始める3ステップ

  1. ゴールをテストにできる形で書く「直したい入力」「期待する出力」「変えない動作」を指定。別ブランチを使い、リポジトリの指示ファイルや既存テストを確認してから、変更候補と実行するテストを説明させます。
  2. 失敗を再現してから、最小限だけ直す不具合を再現するテストを追加し、期待した理由で失敗することを確認。最小限の修正後に同じテストを実行し、これまで動いていたケースも確かめます。再現できない場合は推測で書き換えず、足りない条件を確認します。[4]
  3. 差分と実行結果を人が確認する変更点、実際に実行したコマンド、成功・失敗・未実行を分けて報告させます。共有リポジトリではPRにまとめ、CIの実行結果とレビューを通してからマージします。[5]

コピペ用：既存の挙動を壊さずに修正する

架空の表示フォーマッターを直す例です。実際の依頼では対象ファイルとテストコマンドを自分の環境に置き換えてください。

エージェントへの依頼文
目的：項目がゼロ件のとき、一覧の表示を「項目なし」にする。

受け入れ条件：
- [] → 「項目なし」
- ["A"] → 「A」
- ["A", "B"] → 「A、B」
- 関数の名前・引数と、空でない場合の出力は変えない。

進め方：
1. 既存の実装とテストを読み、変更候補と確認手順を示す。
2. 空入力のテストを追加し、修正前に期待した理由で失敗することを確認する。
3. 最小差分で直し、空・1件・複数件をテストする。
4. 変更ファイル、実行コマンド、結果、未実行の確認項目を報告する。

範囲：実装と対応するテストのみ。依存追加、CI変更、push・デプロイはしない。
再現できない、または範囲外の変更が必要な場合は、そこで止めて確認する。

マージ前に、ここは人が見る

  • 新しいテストは修正前に失敗し、修正後に通ったか。既存ケースも通ったか。
  • テストの期待値を緩めたり、無関係なファイルや設定を変えたりしていないか。
  • 対象環境でCIが動いたか。実行できなかったことを「確認済み」にしていないか。

たとえばAzure Reposでは、PRのビルド検証と必要なレビュアーをブランチポリシーで設定できます。AIのレビューコメントと、人による承認・CIの結果は分けて扱います。
