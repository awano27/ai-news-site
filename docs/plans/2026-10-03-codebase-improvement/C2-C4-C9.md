Date: 2026-10-03 JST

Scope: local implementation and fixture validation only. No stage, commit, push, deploy, real collection, or secrets/settings change.

## Findings before the change

- **C2 reproduced.** Every file named by the review was present locally but excluded by broad `.gitignore` rules. `git ls-files --error-unmatch` did not establish any of them as distributed files. The ingest workflow also installs the ignored `requirements-ingest.txt`; its `pip install -e .` dependency, `setup.py`, is already tracked.
- **C2 secret boundary.** The source/config files reference `PH_TOKEN`, `GITHUB_TOKEN`, `X_BEARER_TOKEN`, and model keys only through environment variables. The reviewed YAML/config did not contain credential values. `sources.yaml` is non-secret source configuration.
- **C4 reproduced.** Eight scheduled workflows commit and push with the repository `GITHUB_TOKEN`, then rely on separate `push` triggers in Pages/presentation/freshness workflows. Those pushes do not start a second workflow. The cloud daily-report workflow has the same publication boundary and shares C3's run-manifest gate.
- **C9 reproduced.** `pages-heal.yml` had only `contents: read`, called the legacy Pages build endpoint, and converted a rejected request into a green step with `|| true`. It did not distinguish an accepted rebuild request from a recovered site.

## Changes

### C2 clean-checkout dependencies

- Added narrow `.gitignore` exceptions for the exact runtime files used by the news, ingest, presentation, and heal entrypoints. Broad ignore rules remain in place.
- Added a clean-tree fixture test. It composes tracked files plus the explicit pending-tracking list in a temporary directory, imports every C2 entrypoint, and runs offline fixture generation for `build_news`, ingest, validation, and detail analysis.
- Included the shared public-HTML inventory in that planned tree and ran analytics injection/coverage against a temporary fixture page.
- Kept API credentials in environment variables. No credential or real API value was copied into a tracked candidate.
- Hardened `detail_analysis_generator.py` chart serialization so `</script>`, `<`, `>`, and `&` in data cannot terminate the script element.

### C4 exact-SHA generation → validation → Pages

- Added reusable `publish-generated-content.yml`.
- Each in-scope auto-push workflow records `git rev-parse HEAD` only after a successful commit/push and passes that exact SHA to the reusable publication path.
- The reusable path checks out the same SHA in `freshness-guard.yml`; Pages checks out that same SHA only after validation succeeds.
- The Pages checkout rebuilds homepage/sitemap, injects analytics into the temporary artifact, and reruns freshness plus analytics configuration/coverage gates before stripping development files.
- The reusable freshness call skips the raw tracked-page coverage step because the next Pages job fixes that packaging concern in its temporary checkout and gates the resulting artifact. Scheduled/push freshness runs still report raw-source coverage drift.
- The uploaded artifact contains `deployment-revision.json` with the actual checked-out `git rev-parse HEAD`; post-deploy verification requires that exact SHA, rather than accepting HTTP 200 alone.
- `pages.yml` accepts a required `ref` for reusable calls and an optional `ref` for manual recovery. Existing push/manual/schedule entrypoints remain available.
- Same-SHA publication is grouped by concurrency, and Pages retains its single deployment concurrency group. No PAT or external service was introduced.

### C9 visible self-heal outcomes

- Replaced the legacy Pages build API call with an explicit dispatch of `pages.yml` using the current default-branch SHA as an input.
- Granted the heal workflow only `contents: read` and `actions: write`.
- Split observation into initial URL probe, dispatch acceptance/run discovery, dispatched workflow completion, and post-deploy URL probe.
- Added `script/pages_heal.py`, a deterministic state classifier. Dispatch rejection, accepted-but-unconfirmed rebuild, and failed recovery exit non-zero; only an already healthy site or verified recovery exits zero.

## Limitations and follow-up

- The pending files are now visible to Git but remain untracked. A fixture that adds the stated list proves the intended clean-tree contents before commit; only a later commit and CI run can prove repository distribution.
- The strict publication gates currently block a release in this baseline: `check_site_freshness.py` reports the missing 2026-09-12 slide and missing index entries for 2026-09-10/11; analytics config is still `G-REPLACE-ME`. Stored coverage also reports five missing pages, while the temporary Pages artifact injection path is covered by fixture tests. These are observed blockers, not repaired content or a deploy result.
- GitHub-hosted workflow syntax was checked by YAML parsing and actionlint; permission/runtime behavior still requires an actual Actions run.
- The self-heal path deliberately fails when dispatch is merely accepted but no workflow run/recovery can be observed. This prevents a green false recovery but may expose repository-level Actions policy restrictions that require an administrator decision.
- C3's run manifest is a separate publication-readiness gate. The C4 SHA handoff consumes only a successfully pushed commit; final integration must keep the C3 gate before that push.
