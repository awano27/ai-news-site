# AIニュースの日本語を読みやすくする編集手順

更新日: 2026-10-16。日次AIニュースの新規作成・既存記事の日本語修正・課題解決型の再構成で使う。2026-10-16号でユーザーが評価した修正を、別の製品や日付にも使える判断基準としてまとめたもの。

**目的は文章を短くすることではなく、読者が「何が新しいか・誰に役立つか・何ができるか・どこまで任せてよいか」を説明できるようにすること。技術的な意味と事実の確度は変えない。**

## 1. 修正対象と範囲を確定する

対象URLの本文・HTML・図・出典を読む。会話に承認済みの修正版HTMLがある場合は、その実体と公開版を区別する。記事を読む前に、一般的な言い換え案だけを作らない。

- **日本語だけの修正**: 既存デザイン・題材・日付・操作を維持し、見出し、導入、分かりづらい本文、対応する図中の文言を直す。理解を妨げる順序だけを必要な範囲で変更する。
- **新規号・全面再構成**: 下記の読者順で構成を組み立てる。既存の調査・図解手順と併用する。
- **Skill保存だけ**: 手順と参照導線だけを保存する。承認済みHTMLの公開、一覧・カバー・サイトマップの更新は別の依頼として扱う。

料金、利用回数、対応形式、保存条件、提供開始日などの変動する事実を記事で扱うときは一次情報を確認する。出典を読めない場合は確認できなかった範囲を明示し、強い断定に書き換えない。この資料の製品名・数字・料金を、別の記事の最新仕様として流用しない。

## 2. 読者が知りたい順に整理する

導入は **発表主体・製品名 → 今回の新しさ → 具体的にできること → 対象読者** を短い段落で示す。既存機能と今回の更新は分ける。

本文の標準順は **何ができる → 誰のどんな仕事に役立つ → 仕組みと数字の意味 → 利用方法・費用 → 制約と確認事項 → 最初に試すこと**。全記事を固定の章数にそろえる必要はない。利用判断を変える重要な制約は、利点を説明する箇所にも添える。

タイトル・小見出しを先に読み直す。「作る速さに、確かめる力を追いつかせる」のような標語ではなく、何を確認し、誰が判断するのかが分かる見出しにする。製品名だけ、問いかけだけで終わらせない。

各段落では主張を1つに絞り、必要なら **結論 → 具体例 → 条件** に分ける。1文を機械的な文字数で切らず、主語や条件を残す。

## 3. 分かりづらさを判定して直す

修正候補ごとに **元の表現 → 読者が答えられない問い → 言い換え → 残すべき意味・条件** を整理する。単語の一括置換ではなく、前後の文と見出しを読んで判断する。

| 読者がつまずく原因 | 判定する問い | 修正の方法 |
|---|---|---|
| 抽象語だけで行動が見えない | 誰が、何を対象に、何をするのか？ | 「確認候補」「力」「活用」を、見直す箇所・確認する人・修正する判断などに具体化する。 |
| 主語や対象が省略されている | AIの作業か、人の判断か？ どの資料の話か？ | 必要な主語と目的語を補う。人とAIの役割を別の節にする。 |
| 技術用語だけで意味が止まる | 業務では何が起きるのか？ | 見出しは働きを平易に説明し、本文で正確な用語と仕組みを補う。 |
| 数字の意味が説明されていない | 何を数えた値か？ 誰の評価か？ | 数字と同時に対象・単位・評価主体を示す。割合は分母・条件も確認する。 |
| 否定や編集者の注意が先に来る | 読者が最初に知るべき事実は何か？ | 先にできること・対象・利用条件を説明し、その後に意味する範囲と限界を示す。 |
| 比喩や疑問形が広すぎる | 仕事のどの場面についての問いか？ | 操作・人数・対象を示した具体的な問い、または行動が分かる文にする。 |
| 例の比較条件がそろっていない | 同じ操作・利用者・条件を比較しているか？ | 同じ対象について必要／不要などが食い違う例にする。実資料は誤りと決めつけず条件を確かめる。 |
| 結論と行動の間が飛んでいる | 読んだ後に何を確かめればよいか？ | 対象資料、確認方法、人が判断する点、記録する結果まで示す。 |

## 4. 平易にしても意味を変えない

**技術用語の対応。** 「計算量を多く割り当てる」を「時間をかける」だけに置き換えない。計算量と経過時間は同じではない。見出しを「点検の深さを決める」にしても、本文には「AIが検討するための計算量を多く割り当て、より詳しく調べる」と残す。専門用語は一律に禁止せず、初出に意味や具体例を添える。

**比較条件の対応。** 「会員登録なしで使える」と「ログイン必須」は、別の条件を述べている可能性がある。矛盾の説明用の架空例なら「ログインせずに予約できる」と「予約するにはログインが必要」のように同じ操作にそろえる。実際の仕様書では、登録済み利用者・例外画面などを確認してから判断する。

**数字の対応。** 利用された論文数、発見した誤りの数、指摘の正答率、時間削減率を別の指標として扱う。「16,000件以上は正答率ではない」だけでなく、まず「前身ツールが利用された論文16,000本以上」と何を数えた値かを書く。前身ツールの実績を現行製品の実測へ移し替えない。

**確度と制約の対応。** 公式仕様、開発元の評価、編集部の想定例、当サイトの実測、未検証を分ける。「候補を挙げる」を「必ず見つける」に、「対応予定」を「対応済み」にしない。「並列に処理する」と「複数ファイルを入力できる」も区別する。「学習に使わない」と「保存しない」「社内機密を送ってよい」は別に説明する。

**注意書きの対応。** 「未検証」「1ファイルのみ」など、判断を変える制約は残す。一方、「〜とは書けません」「長文転載や架空の実測は行っていません」のような編集上の自己説明は、読者が必要とする事実に直す。例: 「掲載例は実際の利用結果ではありません」。

## 5. 修正前後の見本

以下は2026-10-16号の修正で使った表現。表現の対応例であり、製品の最新仕様を保証する一覧ではない。周辺の出典・条件・注記とセットで判断する。

| 修正前 | 修正後の基準例 | 判断の理由 |
|---|---|---|
| 確認候補をAIが出し、根拠を人が確かめる。 | AIが見直す箇所を示し、人が修正するか決める。 | AIが示す対象と、人の判断を明確にする。 |
| 計算を配分する | 点検の深さを決める | 見出しは働きを説明し、本文で計算量の意味を補う。 |
| 並列にレビューする | 複数のAIで分担する | 「並列」の主体を示す。本文には同時に点検する仕組みも残す。 |
| 統合し、根拠を確認する | 結果を突き合わせる | 何をまとめて何と比較するのかを本文で説明する。 |
| 資料間の確認負担にもつながる話 | 初期版で確認できるのは、1ファイルずつです。 | 抽象的な意義より、現在の対象範囲を先に伝える。 |
| 16,000件以上は利用規模。正答率ではない。 | 前身ツールは論文16,000本以上で利用。 | 数字の対象と主体を先に示す。精度を表さないことは本文で補う。 |
| 入口と無料枠 | 利用方法と無料で使える回数 | 読者が知りたい内容をそのまま見出しにする。 |
| そのグラフで、全顧客を語れる？ | 20人の結果を、全顧客に当てはめてよい？ | 抽象的な問いを、対象人数と一般化の判断にする。 |
| 最初の1件は、人が答え合わせできる資料で。 | まずは、内容をよく知っている資料1つで試す。 | 読者が選ぶ資料と行動を示す。機密に関する条件も残す。 |
| 作る速さに、確かめる力を追いつかせる。 | 資料の確認をAIに手伝わせ、修正は人が判断する。 | 標語を、人とAIの具体的な役割に変える。 |

## 6. HTML全体の文言をそろえる

本文だけを直して終わらせない。変更した主張が現れる場所を検索し、次の各面を確認する。すべてを同じ長さの文章にするのではなく、短い表示でも意味・数値・制約が矛盾しないようにする。

| 確認する面 | 主な対象 |
|---|---|
| 読者に見える本文 | h1・副題・導入・h2/h3・目次・カード・表・注意書き・結論 |
| 要点図 | SVG内のtext、画像内の文字、図のタイトル、キャプション、拡大表示 |
| 代替表示 | alt、SVGのtitle/desc、ARIAラベル、図のテキスト版 |
| コピーして使う文面 | textarea、コピー用データ、説明欄、操作ラベル |
| 検索・共有用の情報 | title、description、OG/Twitterのタイトルと説明、JSON-LDのheadline/description |

ニュースの日付、canonical、リンク、ID、イベント処理を不用意に変更しない。JSON-LDは文章を更新した後もJSONとして読めることを確認する。図の文字は長くすると領域からはみ出すため、文字サイズを極端に下げる前に文を分ける・配置を調整する。

画像内の旧文言はaltの変更だけでは直らない。対象画像の実体を確認して修正する。修正できない箇所は残件として伝える。外部のOGカバーや一覧カードを更新するのは、依頼された公開範囲に従う。

## 7. 納品前の確認

1. **見出しだけを読む。** 何ができるか、誰に役立つか、使う条件、次の行動が分かるか。
2. **導入と具体例を読む。** ニュースの新しさを説明できるか。例の主語・操作・比較条件がそろっているか。
3. **意味と事実を突き合わせる。** 数字の単位・主体、技術的意味、出典、予定／提供済み、想定／実測、未確認を保っているか。
4. **表示面を突き合わせる。** 本文、図、図のテキスト版、コピー文、メタ情報に旧表現や条件の食い違いが残っていないか。
5. **ブラウザで確認する。** スマートフォン相当の360〜390px、タブレット相当の768px、PC相当の1440pxを目安に、折返し、SVGの文字、横はみ出しを確認する。図の拡大・閉じる・Esc・フォーカス復帰・コピー・HTML保存など、存在する操作を試す。ログやスクリーンショットを残す。

行った検証と未実施を分ける。HTMLを読んだだけで表示確認済みとはしない。ファイル作成済み、GitHub保存済み、公開URL反映済みも別々に報告する。

納品時は修正版HTMLを提示し、主な修正を元の表現／修正後／理由で少数示す。記事全体をチャットに重複掲載しない。公開依頼がない場合は、未公開であることを明記する。

## 8. 再利用時の回帰チェック

Skill自体を変更するときは、次の入力について修正文と残すべき条件を実際に書き出す。語句の一致だけでは自然さや意味の同一性を判定できないため、修正文を読む。

| 入力・場面 | 合格する判断 | 不合格例 |
|---|---|---|
| 「計算を配分する」を簡単にしたい | 見出しは機能を平易にし、本文に計算量の説明を残す。 | 「長く待てば精度が上がる」と言い換える。 |
| 「利用件数2万件。精度ではない」 | 何の利用件数か根拠を確かめ、対象・主体・単位を示す。不明なら不明とする。 | 利用者数・成功数・正答率を推測で補う。 |
| 「会員登録不要」と「ログイン必須」 | 両立する条件を確かめる。架空の矛盾例を作るなら同じ操作でそろえる。 | 登録とログインを同じ意味として矛盾と断定する。 |
| 「複数AIで並列確認。複数ファイル対応は予定」 | 分担処理の説明と入力制約を別に残す。 | 「複数資料をまとめてチェックできる」にする。 |
| 「学習に不使用。表示用に保存」 | 学習利用と保存を分けて説明する。 | 「送った文書は残らない」にする。 |
| 承認済み本文と図・コピー文の旧表現が混在 | 表示面を一覧化し、同じ意味にそろえる。修正できない面は残件にする。 | h1と本文だけ変更して全体修正済みとする。 |
| 「日本語だけ直して」または「Skillに残して」 | 指定された範囲の成果物を作り、公開状態を分けて報告する。 | ニュースの再選定・無断公開・別デザインへの全面変更をする。 |
| 「初版と比較して新しくなった点が不明」 | 初版の機能と今回の変更を出典に沿って分け、変更点を導入へ移す。 | 製品紹介だけを短くして更新内容を残さない。 |

独立したエージェントで試せる場合は同じ入力を改訂前後で比較する。試せない場合は、静的な参照・形式検査と手作業の例文レビューまでを行い、独立したエージェントでの再現性は未検証と記録する。文書内にルールが存在することだけで、将来の出力品質を保証しない。
